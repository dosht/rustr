# P3 processor review

Read-only source review against `opus/processor-handoff.md`, captured `frontend/services/free-tools-processor`, API-022..030, RTL-006..008, CRN-008/009 and OPS-D06. No builds, tests, formatters, provider calls or source changes. The owner's compressed-JSON, invalid-PORT, sibling-process cancellation and ZIP/base64 work is excluded from duplicate findings.

## Findings

1. **P1: Completed HTTP/1 downloads do not reach the cleanup callback (API-030).** `transgate/processor/src/http.rs:247`, `Streamed::poll_next`, invokes `on_end` only on an additional poll after every segment has ended. `stream` at line 275 supplies `Content-Length`. Installed Hyper's `proto/h1/dispatch.rs:392` drops the body when `can_write_body()` becomes false; `conn.rs:731` changes out of `Writing::Body` when the length encoder reaches zero. Thus a normal complete file or ZIP download can deliver every advertised byte without that final EOF poll: the session and files remain until TTL, and trim never marks the delivered part/ZIP. This differs from the source's `fileStream.on('end')` cleanup (`routes/convert-audio.ts:567-570`). **Required behavior:** completion must follow the last successfully produced declared byte without requiring another consumer poll. Preserve non-completion on early drop/read failure; handle zero-length and HEAD explicitly. Validate through actual HTTP/1 full and aborted downloads, both trim parts and ZIP, with session/files assertions. Directly draining the stream is insufficient evidence.

2. **P1: Waveform decoding doubles an already large allocation and can kill the single processor (API-023, API-029, OPS-D06).** `transgate/processor/src/families/trim_audio.rs:169` reads the entire decoded raw file, then `peaks` at line 178 allocates another full `Vec<f32>`. Source `routes/trim-audio.ts:94-96` uses a `Float32Array` view of the same buffer. A valid 20-hour, 32 kbps MP3 is about 288 MB, below the 1 GiB limit, but its 4 kHz mono f32 waveform is 1.152 GB; the two Rust allocations require 2.304 GB before overhead, exceeding the supplied compose `mem_limit: 2g`. Upload has no processing allowance, so this occurs before the limited trim operation. **Required behavior:** derive the sample count from file size and stream the raw samples into the same 200 floor-sized peak blocks, preserving source remainder/short-file behavior and cleanup. No new duration or product size restriction is needed. Verify peak equivalence over chunk boundaries and bounded memory on long decoded input.

3. **P2: A boundary prefix inside valid file bytes is misread as a multipart delimiter (API-023, API-029).** `transgate/processor/src/upload.rs:364`, `Multipart::step` in `State::Body`, commits a part boundary on any `\r\n--<boundary>` prefix before checking the following bytes. With boundary `XyZ`, file bytes `abc\r\n--XyZXdef\r\nrest` followed later by the real delimiter cause `AfterBoundary` to reject `Xdef` as a malformed boundary line. The captured Formidable parser (`frontend/node_modules/formidable/src/parsers/Multipart.js:263-311`) checks CRLF/closing suffixes and returns false matches to part data through its lookbehind buffer. **Required behavior:** keep candidate delimiters pending until the suffix is valid; otherwise emit the complete candidate unchanged as file data. Add byte-equality cases for near-boundary content and suffixes split across frames, including valid media containing those bytes. The existing tiny-chunk tests do not cover a false delimiter inside the payload.

The owner was asked factual questions about all three observations without an automatic edit request. Their visible response confirms the Content-Length lifecycle bug and absent waveform fix, and indicates repair work is starting. Findings remain open pending source handoff and lead execution evidence; a repair intention is not verification.

## Narrow repair re-review: four edge cases

The first repair handoff addressed the original delimiter-prefix rejection, whole-waveform allocation and final-byte callback defect, but exposed these four remaining counterexamples, sent to p1W and lead:

1. **P2, waveform parity:** `trim_audio.rs::Peaks::feed` reset `carried` to zero after two successive one-byte reads, losing an incomplete f32. Partial carry must survive until all four bytes arrive.
2. **P2, child lifecycle:** `media.rs::output_until` stopped selecting timeout/cancellation after both pipes reached EOF, then awaited the child unguarded. A child that closes stdout/stderr and stays alive could evade its deadline or sibling cancellation. Both signals must remain active through child exit; failure must kill and reap before return.
3. **P1, JSON resource containment:** `http.rs::Decoded` inflated each compressed frame into an unrestricted `Vec` before checking the 100 KiB limit. A small compressed frame could allocate far beyond that limit. The decoder's output writer must enforce the cap before appending, including finalization.
4. **P2, download completion (API-030):** `http.rs::Streamed::poll_next` still called completion on EOF with `remaining > 0`. A file truncated after stat could therefore trigger successful-download cleanup. Short EOF/read failure must disable completion and fail the response body.

Current source inspection finds all four narrow corrections present: `Peaks::feed` returns with incomplete carry intact; `output_until` selects over pipe reads plus child wait; `Capped::write` bounds decoder output; `Streamed` suppresses completion on errors and emits `UnexpectedEof` for a short body. This is source disposition only, not execution closure. Lead must run the corresponding short-read, closed-pipe child, compressed-expansion and truncated-download regressions plus actual HTTP download cleanup. No builds, tests or formatters were run in this review.
