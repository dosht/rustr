This supersedes conflicting recommendations in my independent proposal. I read `opus/proposal.md` and `opus/critique.md` and discussed the differences directly with Opus w23:p1X. ## Corrections and concessions

**1. Preserve the original Soniox money path.** I withdraw any implication that a GET used for callback verification should supply missing webhook duration. Opus correctly separated the paths. Source `frontend/src/utils/soniox.ts:137-174` uses positive `reported.audio_duration_ms`, otherwise max token `end_ms`, and overwrites internal `metadata.duration_ms` with that value. The webhook passes its received field (`frontend/src/pages/api/soniox/callback.ts:139-143`); recovery passes the status-poll observation (`frontend/src/utils/sonioxRetry.ts:130-153`). A verification GET is not the original webhook observation.

Counterexample: unknown-duration job, webhook without duration, token max 60000 ms, GET audio duration 60001 ms. Source webhook billing is one minute; enriching it from GET makes two. The original recovery path can legitimately use the second value. Persist origin and optional reported duration before acknowledging the webhook, and preserve them on inbox retry. First eligible terminal commit wins; a later poll cannot reprice completion. The documented webhook shape is not proof that real deliveries always omit the optional field. [Soniox webhooks](https://soniox.com/docs/stt/async/webhooks).

**2. Preserve last-write-wins editing.** Opus is right: my required expected line revision introduced a new user-visible restriction. EDT-002/003 permit empty edits, with no revision/status/age condition (`frontend/src/features/transcriptLines/services/TranscriptLineService.ts:76-98`). Two editors saving the same existing line must retain source last-write-wins behavior, not return a new stale-revision 409. Internal account/job locks, owner checks and update-only commands still prevent resurrection after retention/erasure. Speaker rename remains one atomic update of matching existing lines. Optimistic editing needs a separate approved outcome change.

**3. Pins are first attempts, not exclusive candidates.** Opus conceded that its original pinned-only route was wrong: `frontend/src/services/unified-transcription/services/transcription.ts:505-558` executes the pin without manager validation, then calls `handleFailover` on failure when enabled. That fallback filters translation/capability/availability (`provider-manager.ts:516-594`). My universal pin validation also needs a recorded correction, not a claim of source parity. We agree to preserve compatible pins as first attempts, represent removed RunPod as unavailable, then try compatible alternatives when enabled. Incompatible pins and unconditional Soniox last resort get explicit correction records. Capacity shortage queues; absence of any compatible configured provider fails. No invisible conversion of a pinned translation into plain transcription.

**4. Shared protocols are smaller than two independent integrations.** Opus withdrew malware scanning and per-host duplication. The taskr sample now uses the same Soniox/Deepgram/storage adapters, a small own `Work` aggregate and an explicit audio-work route. Shared crates contain transport contracts and protocol implementations only. Product lifecycle, routing, segmentation, privacy and billing composition remain host-owned. A small common PG advisory-lock/schedule-slot adapter is acceptable; no scheduler/workflow framework. Both consumers exercise the P3 billing erasure extension. Ordinary task creation and `taskr-core` stay unchanged.

## Concrete correctness gaps resolved with Opus

**P1: Durable intake must preserve both payment facts and erasure barriers.** Opus's original Soniox 200-before-work and Deepgram retry-only approach could lose paid results. Both now use a narrow authenticated inbox committed before 2xx. Soniox stores id, status, attempt, original optional duration and observation origin; Deepgram stores its result body until ingestion commits. Intake and ingestion check the erasure barrier in the account-first transaction. Transient storage errors retry; deterministic invalid/no-speech outcomes remain coded failures. A savepoint isolates deferred debit failure so completion can still commit. Raw payload archival remains best effort, but its keys and in-flight writes participate in erasure.

**P1: A closed deletion record must still deny access.** Opus initially checked the barrier only while deletion was open (`opus/proposal.md`, section 6). A still-valid JWT after closure could pass that check and reprovision an account/trial. We agree on a surviving tombstone, checked by provisioning, directory refresh, workers and signed-resource issuance, including after account locking/creation inside transactions. The UUID is a linkable pseudonymous identifier; omitting email/name is not proof of anonymization. Removal is an explicit policy, not a timer based only on JWT expiry.

**P1: Account erasure needs a union of owners, not repeated single-subject release.** The saved `release_subject_charges` is the right single-subject P2 seam (`modules/billing/core/src/app.rs:1635`), and requires being the first billing call. Looping it for several jobs can lock owners 1 and 3, then discover owner 2, reversing order against another transaction. The P3 extension must discover owners for all erased subjects, account-attributed usage and account-owned packages together, lock ascending, reread and refuse/retry if the set changed. It restores signed cross-owner package sums without deleting unrelated surviving jobs. This is P3 module-extension work, not a new P2 release prerequisite.

**P1: Remote exceptions are not successful erasure.** Supabase `jobs` bucket objects are separate from GCS/R2 audio (`frontend/src/utils/{soniox,deepgram}.ts` raw-payload writes). They require Storage API deletion before GoTrue where ownership blocks auth deletion. Neither SQL metadata removal nor a synthetic GCS smoke proves that path. Soniox 409, GCS retention refusal, uncertain attempts and recreated objects after an outstanding PUT must stay in durable recovery. Unsupported remote deletion can only finish as an approved recorded exception, never as confirmed deletion. An exception-labeled UI state must not stop required retries. [Supabase object deletion](https://supabase.com/docs/guides/storage/management/delete-objects), [user management](https://supabase.com/docs/guides/auth/managing-user-data).

**P1: Cleanup audit and preference races need transactional proof.** Opus accepts sorted candidate-account locking and rereading opt-outs, one atomic bounded deletion transaction, and durable failure/skip/abort records outside rolled-back work. The source CHECK excludes `skipped/aborted`, and failure logging followed by RAISE cannot establish committed evidence (`20251222100000_move_cleanup_audit_to_audit_schema.sql:23-35`; `20251222100001_update_cleanup_functions_audit_schema.sql:50-78,101-125,174-203`). Exactly 100000 is allowed; 100001 deletes nothing. History remains the separate browser-calendar calculation, including month-end overflow; weekly run-history purge preserves `90 + 1 day`, not a silent 90-day cutoff.

## Scope reductions I accept, with their limits

I withdraw mandatory external-audio staging and immutable submission copies. Preserve direct provider fetch, record generation where available and retain source client-duration trust. This does not prove provider-side redirect/DNS behavior safe; that evidence limit and the DNS-failure validation policy stay explicit. Host-controlled outbound requests need their own connection-time protections. No new proxy or copy subsystem is needed to dispatch P3.

AI consent API/production belongs to P4. P3 provides account erasure participation for data actually present, not a fake AI deleter counted as real coverage. Ordinary draft removal retains JOB-038's no-file-delete result unless a correction is recorded; account erasure includes objects. Storage signing implementation may use configured GCS HMAC interop, but a MinIO round-trip is not proof of GCS retention behavior or compatibility with existing RSA-only deployment credentials.

The full 526-rule ledger and all parity obligations remain intact. A phase manifest is a dependency/evidence index, not permission to turn a mixed row green or remove it from final validation. PRV-053 through PRV-060 are not resolved merely by assigning legal copy to P6; their technical/privacy contradictions remain visible. Original proposals' phase gates must not redefine the final denominator.
