# Taskr P3 source review

Read-only review of taskr-work, taskr-billing's enrolled-sample erasure hook/migration, and taskr-server composition against the frozen contract, D1–D11 and convergence clauses 3–5, 7, 10–12. No builds, tests, runtime or provider calls. Runtime consequences below are **[INFERENCE] from source interleavings**, not reproduced failures. Findings refer to inspected app.rs snapshot CBD0, store.rs 66F5 and work.rs D1A0; Sonnet was notified directly and may be repairing them concurrently.

## Actionable findings

1. **P1 — Version-pinned erasure can complete while a replacement upload survives.** `app.rs:335` binds HEAD's object generation; `store.rs:444` manifests that exact version. `app.rs:727–732` deletes it again after the PUT grace period, not the newly created generation at the same key. A still-valid PUT after the first delete creates generation B; deleting absent generation A then marks cleanup done. Keep the known-generation deletion and an independently tracked current-key re-sweep after capability expiry. Also `app.rs:735` replaces the capability deadline with a provider retention deadline: preserve the later deadline, otherwise a shorter retention hold permits premature completion. The owner has begun making the object fixture generation-aware; the inspected implementation remains unchanged.

2. **P1 — Terminal callback handling bypasses identity/conflicting-payload checks.** `work.rs:293–298` calls `live()` before comparing the bound remote; `app.rs:493–497` turns that stale error into successful ignore. Hold callback B after verification against an unbound attempt, let callback A bind and **complete**, then release B: B's different remote becomes 2xx rather than 409. The existing service race test uses processing(A), so does not cover this terminal case. Same-id changed terminal payloads are also indistinguishable from exact replay; no persisted digest/intake comparison exists, and `work/tests.rs:119–126` explicitly accepts changed text as an unchanged result. Check identity and durable payload conflict before terminal/stale replay handling; retain exactly-once result application.

3. **P1 — Unidentified erasure reconciliation discards ambiguity and original project.** `store.rs:449` saves provider/reference/attempt but omits the original project and submitted request correlation facts. `app.rs:775–780` selects the first callback-URL substring match and replaces the unidentified resource with that one remote. Multiple matching jobs therefore collapse to one deletion and can falsely close the saga; a changed configured project is not checked against the original one. Persist original identity/request facts, parse exact callback parameters, and leave ambiguous matches unresolved rather than choosing the first. Add multi-match and project-change regressions.

4. **P1 — Retention can delete after opt-out has committed.** `store.rs:309–314` filters preference only during candidate discovery. `app.rs:618` subsequently locks the account through `update`, but ignores the freshly loaded enrollment and tests only work age/status. Opt-out between those operations still loses the transcript. Recheck `Enrollment.auto_delete` under the same account lock used by settings before deleting. The existing retention service test toggles preference before candidate discovery; add the selection/opt-out/purge interleaving.

5. **P2 — A temporary remote deletion refusal becomes permanently unscheduled.** `app.rs:753–755` stores `Retained { until: None }` as `unresolved`; `drive_erasure` at `704–713` only drives remote rows in `pending|blocked`. A provider processing-state refusal therefore never gets retried after processing finishes. Keep transient retention runnable, distinct from genuine unsupported/manual-unresolved cleanup. Regression: Retained-without-deadline, restart/pass, then Deleted closes that resource.

6. **P1 — Erased accounts can monopolize every bounded work/recovery batch.** `store.rs:265–305` does not exclude durable erasure barriers. D10 deliberately retains rows while subscription termination is unresolved. If such an account owns at least one batch of oldest uploaded jobs, every dispatch pass selects them, fails the live-account check, and selects them again; newer live accounts never run. Expired/running recovery scans have the same eligibility defect. Exclude barred accounts before LIMIT, while retaining the locked recheck. Test a blocked erasure ahead of another live account with a small batch.

7. **P2 — Soniox listing misses authorize fallback despite the frozen unresolved policy.** `app.rs:538–565` supersedes an uncertain attempt on zero matches (or unsupported listing), allowing another provider submission. Convergence clause 5 requires no-match/multiple-match reconciliation to remain unresolved; no taskr-specific exception was found in the approved documents. The lost-answer service test explicitly expects fallback after a miss. Preserve unresolved Soniox acceptance and the original correlation facts; do not confuse the separately approved Deepgram stuck-work policy with proof of Soniox nonacceptance. If a different sample policy is intended, obtain an explicit contract decision rather than pinning this behavior as parity.

8. **P1 — Late authenticated/accepted remote identities are discarded instead of retained for erasure.** `work.rs:293–305` rejects superseded attempts before recording a newly learned remote. `app.rs:414–421` ignores the nested stale error, and `479–497` acknowledges stale callbacks without preserving that identity. If erasure already removed the attempt, `app.rs:424–426` attempts one remote delete and discards its outcome without updating the unidentified manifest entry. A later refusal/network loss leaves an actually known remote permanently unknown (especially problematic when listing is unsupported). Preserve late identities in the old-attempt/resource manifest without changing current work lifecycle; persist a late ACK into the erasure resource before cleanup I/O. Cover delayed ACK/callback after supersession and after the erasure barrier with a retained/error deletion outcome.

## Boundary assessment

The inspected production paths take billing account locks before sample/work locks; directory upsert's insert trigger acquires its shared sample fence before conflict-row update. Ordinary task/workspace routes remain additive and outside the explicit sample erasure. This is a source assessment, not new runtime evidence. The successful-path atomicity test alone does not prove rollback behavior; lead owns integrated verification.

### Interleavings corrected during this re-review

The initially inspected repair still dropped authenticated callbacks that crossed erasure, omitted terminal digests on recovery polls, discarded listing matches after an ACK converted their resource, and allowed stale unresolved updates to park that converted resource. Sonnet repaired these after direct factual feedback. The final handoff now describes normalized-result digests accurately.

The additional per-account session lock around erasure advancement avoids ordinary duplicate driver I/O, but is **not** the durable correctness boundary: its connection can disappear while a provider listing is awaited. The final account-locked `identify_resource` accepts the account independently of the old row, preserves returned identities after another driver has finished, and reopens the saga. `a_listing_result_that_arrives_after_the_erasure_closed_reopens_it_and_is_deleted` exercises the missing-row/closed-saga outcome without pretending to be a process-crash or lock-disconnection test.

### Remaining concrete issue: regression isolation

**P2 — `erasures_that_cannot_finish_do_not_starve_the_ones_behind_them` is not isolated from concurrent global sweeps.** In `tests/service.rs:1052–1065`, two accounts share the database used by other service tests; the test compares ordering before/after a manual `touch_erasure`. Another test's `erasure_pass` can touch either account between those observations and reverse the expected order. `sonnet/host-handoff.md:72` acknowledges this possibility and suggests an isolated rerun. That is not a repair for a nondeterministic suite. Isolate the affected fixture or serialize the global sweep tests; do not use reruns to establish a green result.
