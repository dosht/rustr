# P3 independent Astra proposal

Status: independent design, 2026-10-24. No implementation, build, test, formatter, provider request, production access or secret inspection performed. This proposal does not certify P2 or any P3 gate. The P2 implementation and repair contracts remain the billing integration boundary. No other P3 advisor proposal was consulted.

## 2. Minimal architecture and ownership

Proposed files/crates, subject to lead naming reconciliation before fan-out:

* `transgate/core/src/{jobs,routing,transcript,export,presentation,privacy,ports,languages}.rs`: product aggregate, pure decisions and command/query ports. No HTTP, SQL, provider SDK or subprocess. `languages.rs` follows PRD 7.4. Privacy is a product application concern, not a reusable billing extension.
* `transgate/jobs-postgres/`: jobs, lines, provider attempts/inbox, cleanup runs and erasure manifests, plus the host-owned transaction adapter that uses the existing billing transaction. One new schema/migration history, not migration version collisions with billing/auth. Owner provisioning is separate from restricted runtime.
* `crates/media-ports/`: only provider/storage protocol value types and ports shared by the two consumers: source reference, submission/result/status, transcription request, normalized result, object identity and temporary access. No Transgate job statuses, retry policy, language picker, billing or privacy policy.
* `crates/media-adapters/`: Soniox, Deepgram, GCS and R2 transports with configured endpoints and credentials, plus the narrow legacy Supabase object access needed below. Concrete scheduler/PG lock adapters can live with existing infrastructure; do not create a generic workflow executor or plugin registry.
* Existing `transgate/server`: authenticated HTTP composition, worker/scheduler entry points and mail/analytics sinks. It calls application commands, never decides billing or routing. A separate `transgate/processor` binary/service owns FFmpeg and temporary free-tool files.
* `crates/taskr-work/`: a small second consumer with its own aggregate, persistence and HTTP application adapter using media ports/adapters. `taskr-core` remains dependency-free and ordinary task creation unchanged. Existing taskr server composes it explicitly.

`Job` contains all twelve persisted statuses, revision, owner, source, language/options, duration, provider binding, timestamps and error. Operational attempt/lease fields do not create new user-facing statuses. Imported `uploaded/processing/ready`, `speaker_labeling`, RunPod references and historical lines are representable; no lossy enum folding. Domain operations are explicit commands: create/update draft, start batch, claim submit, acknowledge submit, record terminal result, cancel, soft-delete, edit line/speaker, purge, change cleanup preference and request account erasure. Imported records enter through import authority, not public command fields.

Presentation states cover upload queue, transcript editor, history and privacy settings. They emit effects for metadata measurement, signed upload, progress/polling, player seek, export/download, confirmations and logout. The VM owns language/translation availability, default originals/timestamps, speaker labels, loading/error state, pagination and account-specific flags. Browsers only execute effects and render. Existing taskr CAS and same-transaction outbox provide the pattern (`crates/taskr-postgres/src/lib.rs:135-191`); P2 adds account-first locking rather than a competing repository transaction.

The host opener owns commit. Aggregate revisions reject stale commands; provider-attempt identity is independently checked before interpreting a duplicate. A changed payload cannot borrow a prior operation's success. Database constraints enforce unique remote identity per provider, one accepted terminal ingestion per attempt, stable line identity/order, active attempt fencing, and stable outbox target keys. Full transcript replacement and completion happen in one transaction. Edits use their own expected revision plus parent lifecycle check; retention/deletion cannot race a stale edit into resurrecting content.

## 3. Job lifecycle and recovery

| Command/event | Preconditions and atomic result | External work / recovery |
| --- | --- | --- |
| Create draft / upload metadata | Authenticated active owner; server assigns id, object identity and defaults. Duration may be unknown. No charge. | Return short-lived upload capability. Failed PUT leaves the draft. Poll/metadata updates are expected-revision commands, not arbitrary row patches. |
| Start batch | Account lock, ascending owned draft ids, fresh state/options, P2 admission and all charges; update eligible rows to `not_started` and write submit work in the same commit. No eligible rows is an error, not replay success. | After commit, submit sequentially and return source-compatible 201 per-job acceptance/queue/error results plus balances/counts. A disconnect does not lose the committed work. |
| Claim submission | `not_started` or `pending`, active account, matching revision and no live attempt claim. Persist attempt id, request fingerprint, selected provider/model, lease and callback credential before HTTP. | Network outside transaction. Expired worker lease permits reconciliation, not proof that the provider rejected the request. |
| Provider accepts | Only the current attempt can bind its provider request id and change eligible state to `running`, with `started_at`. Unique provider/project/request identity. | Callback arriving before acknowledgement is durably held against the attempt and reconciled. An old acknowledgement cannot overwrite completion, cancellation or deletion. |
| Definite submit rejection | Record attempt failure first. Rate-limit exhaustion of compatible candidates leaves `pending`, increments retry count once for the submit cycle and records time/error. Other definite errors become `failed` only after permitted fallback ends. | Compatible fallback uses a new attempt; it cannot submit after terminalizing the job. `fallbackEnabled=false` remains effective. |
| Ambiguous timeout/lost acknowledgement | Preserve operational uncertainty and attempt identity; do not label a timeout a definite non-acceptance. No second debit. | Wait for authenticated callback; Soniox can reconcile its listing. Deepgram recovery can later resubmit under its existing stuck policy, with explicit duplicate-provider-work risk. |
| Authenticated callback | Validate provider/project/attempt/remote identity before duplicate handling. Store the delivery durably before 2xx. Same identity and same result is no-op; conflicting result is held, not applied. | Soniox result GET occurs outside tx. Deepgram result body must be durably retained because it cannot later be fetched as a transcript. Lease the inbox work, retry after process death. |
| Complete current attempt | Lock account then job; check active account, attempt and lifecycle; insert all normalized lines, discover duration, attempt deferred billing using a savepoint, mark `completed`, record result identity and outbox in one commit. | A database/storage failure retries durable ingestion without partial lines. Deterministic unusable/no-speech/provider failure records the source coded `failed` result. Blob diagnostic archival is best effort and separately recoverable. |
| Recover stuck work | Running for more than 30 minutes; claim against revision/attempt. Soniox uses its existing recovery-attempt CAS and at most three failed ingests, returning the claim on still-processing/status-query failure. Deepgram resets to pending and increments retry count. | Three-minute sweeps, per-job failure isolation. Soniox missing/unrecoverable identity becomes explicit `recovery_unavailable`, not an invented result. Deepgram's source has no retry-count ceiling; a new terminal ceiling needs a decision. |
| Cancel | Only `not_started/pending/running`, active owner and matching revision. Fence attempt, set `canceled`, enqueue any supported remote cleanup. | Local cancellation cannot promise remote cancellation. Late results cannot restore lines or bill. No new cancellation UI and no automatic refund. |
| Edit line / rename speaker | Owned job, expected transcript/line revision; preserve source editing of any retained status, empty text and all matching speaker labels. | Concurrent callback/cleanup/edit produces a conflict or serial result, never stale text resurrection. A provider replay never overwrites user edits. |
| Soft-delete job(s) | Set `deleted`, bump revision and fence work. Preserve source lack of refund and source owner read-by-id behavior until a policy correction explicitly changes it. | Do not call this physical erasure. Draft hard deletion and account erasure use the purge path below. |
| Purge draft/account data | Tombstone/barrier, explicit child deletion, P2 affected-owner locking and signed usage cascade in one local transaction; durable object/provider manifests survive it. | Physical external deletion is retried independently; never lose the keys by cascading the manifest. |

The counterexample that requires attempts is small: worker A sends a request, the provider accepts, A dies before storing the response, and worker B sees an expired lease. A revision alone cannot distinguish that execution from a request never sent. Neither a local outbox nor Soniox `client_reference_id` makes remote execution exactly once. We promise one local terminal application and one charge per eligible transition, not exactly one provider bill.

One retry decision function takes the classified failure, provider capability and current attempt state. It chooses retry-at, compatible fallback, reconciliation or terminal failure. Transport adapters do not independently change job status or run hidden retry loops. Preserve the source three-minute schedules, Deepgram pending-before-not-started oldest-first queue, maximum five submissions per tick, one-second spacing, stop-on-429 and four usable running slots. Count claimed submissions and uncertain live attempts against capacity too, under a provider/project capacity lock, so two replicas cannot each take the last slot. Capacity lock acquisition precedes the short account/job claim transaction consistently; callbacks release slots without taking that lock, avoiding reversed lock order. This is separate from billing's account-first order among account/host/ledger rows.

Soniox pending work must also be picked up: `JOB-026` currently strands 429 results. Apply the same scheduler/claim mechanism without inventing Deepgram's four-slot limit for Soniox. Keep the existing Soniox recovery counter meaning rather than counting still-processing polls as failures. Recovery scans are bounded per tick, with durable next-attempt/cursor state; elapsed leases fence acknowledgements. Do not turn a finite scan limit into a new customer retry limit.

For Soniox lost acknowledgements, page `GET /v1/transcriptions`, matching a newly generated unique local attempt reference and submitted fields, then bind only one consistent remote result. Persist pagination progress; multiple matches or incomplete evidence remain unresolved, never choose the oldest. Its create API explicitly permits duplicate reference values, and listing has cursor pagination with up to 1000 rows. This is reconciliation, not remote idempotency. Imported `job_{id}` references need stronger matching or manual resolution. [Create transcription](https://soniox.com/docs/api-reference/stt/transcriptions/create_transcription), [Get transcriptions](https://soniox.com/docs/api-reference/stt/transcriptions/get_transcriptions).

Durable inbox is narrow and justified by actual callback loss, not a generic command receipt framework. Record only the fields/body needed for processing, with restricted access and lifecycle cleanup. Intake checks the erasure barrier in its account-first transaction, not only before it opens; otherwise it could recreate a raw body after erasure. Successful ingestion can discard the raw inbox body while retaining the minimal duplicate fingerprint; raw object archival must not defeat erasure. A late callback for an erased account is acknowledged only after its known remote identity has been attached to the erasure manifest, without keeping transcript text. Unknown/forged identities do not become new jobs.

## 4. Protocols, routing and media behavior

### Routing and language evidence

One pure router filters by language/model/translation first, then applies existing valid pins, non-translation duration over 250 minutes or `.qta` Deepgram overrides, valid API preference, and Soniox then Deepgram preference. Translation remains Soniox-only with a known source, first distinct target and the source 53-language set. Null language remains Soniox-only even though Deepgram documents detection; do not silently expand the product contract. Grammar correction remains an inert non-RunPod option. Health scoring and RunPod execution are removed by the PRD, not by pretending every language maps to Soniox.

There is a fixture contradiction: `transgate/fixtures/languages/provider-routing.json` says existing pins pass validation, but `frontend/src/services/unified-transcription/services/transcription.ts:505-522` bypasses the manager when a pin exists. The manager itself validates at `provider-manager.ts:245-262`. Proposed correction: validate every pin; retain its value as imported evidence, but refuse incompatible/removed execution instead of silently rewriting it. An imported running Soniox job with an id is recovered as that attempt, never freshly routed. Imported RunPod/legacy processing work requires an explicit cutover disposition; it is readable but not automatically sent to another provider. The baseline Deepgram default is also a pin, not proof the user deliberately selected it. Migration must distinguish known origin rather than erase all defaults heuristically.

### Concrete wire adapters

Soniox submits authenticated `POST /v1/transcriptions` with `audio_url`, model, language identification, optional single language hint, diarization, one-way first-target translation, attempt reference and authenticated webhook. It records the returned id before status/result retrieval. Webhook authentication is mandatory for newly submitted work, using the documented custom header; a job id alone authenticates nothing. Stage notifications, fetch status and transcript through the configured project, validate the association, and normalize `audio_duration_ms` into the source internal `metadata.duration_ms` contract. Callback bodies need not contain duration. Primary API and source `frontend/src/utils/soniox.ts:137-174,207-305` support this distinction. [Soniox create](https://soniox.com/docs/api-reference/stt/transcriptions/create_transcription), [webhooks](https://soniox.com/docs/stt/async/webhooks).

Deepgram submits `POST /v1/listen` with `Authorization: Token`, `{url}`, configured model, explicit language, smart formatting/punctuation/paragraphs/diarization and callback. Preserve the existing account-specific Nova-2 exception as host-owned trusted configuration, with a synthetic account fixture, not a private identifier copied into shared code. Correlate returned `request_id` with callback `metadata.request_id` and the submitted attempt. The documented HTTPS Basic Authentication callback mechanism supplies an attempt credential; redact URL credentials and require it before ingestion. Do not invent a Deepgram signature header. Its callback API documents retries on non-2xx, up to ten with 30-second delays. [Deepgram callbacks](https://developers.deepgram.com/docs/callback). The source wire shape is `frontend/src/utils/deepgram.ts:134-178`.

New secure callbacks must coexist with cutover accounting: old unsigned Deepgram jobs cannot be retroactively given a secret. Quarantine their notifications unless a separately approved verification path establishes ownership and result authenticity. Drain/migrate those in-flight jobs under P9; do not add a permanent unsigned bypass. Soniox old attempts can be verified by authenticated status/result retrieval against an already trusted stored remote id. This is a cutover prerequisite, not permission to erase in-flight work.

Both adapters have finite connection/read/body limits and typed errors; user-facing upload duration remains uncapped as in UPL-005. Provider processing timeouts are not maximum audio durations. Deepgram documentation currently gives differing processing-time limits across its Whisper and model overview pages, so timeout acceptance is an explicit fixture/live prerequisite, not an asserted product duration limit. [Whisper caveats](https://developers.deepgram.com/docs/deepgram-whisper-cloud), [model overview](https://developers.deepgram.com/docs/models-languages-overview).

### Storage and sources

Persist an opaque object reference (provider, bucket, key, generation/version where available), never a presigned URL. Preserve GCS default/R2 choice, `userId=.../jobId=.../{filename}` mapping, 900-second upload/player URLs and fresh 3600-second provider GET URLs. The GCS source uses ordinary V4 write signing despite a misleading resumable-upload comment (`frontend/src/services/storage/providers/gcs.ts:42-69`); do not implement a resumable session protocol by reading the comment alone. R2 uses S3 SigV4 on its S3 endpoint. Neither needs a live signing request for locally held signing credentials. Credentials remain server-only; signed URLs are bearer capabilities and must be redacted. [GCS signed URLs](https://docs.cloud.google.com/storage/docs/access-control/signed-urls), [R2 presigning](https://developers.cloudflare.com/r2/api/s3/presigned-urls/).

Owner authorization precedes signing. The server derives keys; the client cannot name arbitrary buckets, another account or a traversal path. A draft upload command may change only draft fields. Before using uploaded bytes, bind the object generation where supported. Otherwise copy the accepted upload to a private immutable submission key for which no client PUT was issued, and bind that object's identity; do not assume every backend supports GCS generations. Stale PUT URLs must not replace provider input unnoticed. Erasure must include outstanding write capabilities: prevent reissue, wait until their expiry and then sweep again for recreated objects and submission copies. Unexpired read capabilities cannot be revoked merely by a SQL tombstone, especially while a retention lock blocks object deletion; report that residual access honestly.

Browser duration behavior stays in presentation effects: metadata attempt then small-file decode fallback, rounded-up minutes, null on failure; source-specific YouTube rounding remains different. There is no new ten-file server cap because the source UI cap does not constrain multipick. Preserve source picker/drop differences until a recorded decision fixes them. Source rules and locations: UPL-001 through UPL-008, UPL-013 through UPL-021.

External URLs preserve `file_path` then legacy `callback_url` fallback (`JobStorageService.ts:66-91`), with separate typed fields for audio source versus customer webhook. Correct fail-open SSRF validation in UPL-030/API-009: reject non-HTTP(S), credentials, private/reserved destinations and resolution failure; validate every redirect and pin resolved addresses for any server fetch. A validation HEAD alone cannot constrain a provider's later DNS resolution or redirect. For defensible behavior, stream external audio through a controlled fetch into private staging storage, rechecking each hop, then submit its signed URL. This introduces a temporary object, not a new duration/size product limit; its erasure belongs to the manifest. If lead chooses direct provider fetch for compatibility, mark that residual SSRF boundary unproved rather than claiming the fetch guard protects it.

Signed-in YouTube caption resolution and public captions are separate adapters. `TranscriptApiService.ts:18,49-112` calls paid `GET /api/v2/youtube/transcript` with Bearer auth, `video_url`, JSON/timestamps/metadata; source resolver maps captions into an uncharged draft-to-completed transaction. Public `PublicTranscriptService.ts:1-155` uses `youtube-transcript`, with no paid fallback, no job, source error mapping and the six-hour/500-entry cache. Preserve those boundaries and time-unit normalization. [TranscriptAPI reference](https://transcriptapi.com/docs/api/), [youtube-transcript maintainer source](https://github.com/Kakulukian/youtube-transcript). The latter is an unofficial YouTube protocol, so replay success is not proof of current service availability. Port its narrow transport/parser into a Rust adapter with provenance; do not replace free extraction with a charged ASR job or claim an official YouTube caption endpoint offers arbitrary public-video access.

### Transcript, translation, editing and exports

Port the pure normalizers against source-derived fixtures before transport integration: Soniox punctuation/gap/speaker segmentation, short-line merging, `(ms+500)/1000` floor rounding, zero-based padded speaker labels, alternating translation groups and stable original-before-translation ordering; Deepgram first alternative, paragraph sentences then word/speaker fallback, whole-second flooring and no Soniox offset. Preserve YouTube cue flooring and null speaker/language/translation fields, no-speech errors, and imported RunPod fields without executing RunPod. These details are TRX-024 through TRX-032 and TRX-038 through TRX-040, sourced to `frontend/src/utils/{soniox,deepgram}.ts` and the YouTube resolver.

Store one canonical editable line model with stable ordinal/id and language/translation status. Speaker rename affects all matching retained lines atomically, display fallback never changes stored speaker, translated tabs/RTL/default originals and timestamps follow the source VM. Keep corrected text and AI output distinct; P3 must not invent grammar correction or a shared LLM request for translation. `transgate/docs/discovery/ai.md` owns the future LLM port and consent-controlled completion summary.

Exports produce actual ZIP/TXT/CSV/SRT/VTT/Word bytes, not a filename stub. Preserve sanitized base names, translated headings, 30-second speaker grouping, subtitle long-line splitting, arrow escaping and distinct transcript-page versus list/phone translation selection. Preserve EDT-011 text-time sorting and stable equal-time ordering; a new numeric normalization must not silently reorder imported text times. Pin a source oracle fixture per EXP rule. The source writes OOXML under `.doc` (`frontend/src/utils/transcriptFileSaver.ts:134-150,267-417`); recommend a recorded extension correction to `.docx`, not a silent byte/format substitution. Browser clipboard/share/download execution and its EXP-016 analytics effect stay P5. Export/query/stream issuance rechecks active account and owner before reading; stale content caches cannot bypass erasure.

### Server-first free tools

The separate FFmpeg processor remains a real P3 deliverable. Keep seven families, anonymous unguessable session capabilities, per-family temporary directories, the existing CORS surface, separate upload/process requests, trim's 1 GiB limit and others' 2 GiB limit, exact format/quality/rate/channel validation, synchronous audio conversion versus accepted asynchronous operations, download/ZIP semantics and stream-completion cleanup. Preserve API-022 through API-030 and CRN-008/009, not a general jobs/billing interface for anonymous tools.

Implement pure tool validation/planning in the product core and fixed FFmpeg argument construction in the processor adapter, with no shell interpolation or arbitrary paths/URLs. Process non-root with bounded resources, own local volume and explicit health. Local processor session claims prevent concurrent processing; ten-minute sweeps use the source one/two-hour family TTLs based on creation/mtime, skip actively leased streams/processes, and remove restart orphans. A single processor instance per local volume is the minimal supported deployment; multi-replica workers must share durable session claims and storage rather than pretending a process-local map is distributed. Keep CLIENT_WASM_ENABLED=false. Source: `frontend/services/free-tools-processor/src/index.ts:15-50,102-135`, the seven route files enumerated by API-023 through API-030, and `frontend/src/utils/free-tools/clientWasmEnabled.ts:5`.

## 5. Billing integration

Use `docs/plans/p2-billing/{implementation-contract,decisions,repair-contract}.md` as fixed D1-D4 behavior. The host starts the transaction, locks the billing account first, then owned jobs by ascending numeric draft id, then uses P2 ledger operations. All rows and facts are read/rechecked under those locks. Mixed valid/invalid/foreign ids cannot mutate another account; request order does not alter allocation. Billing, state changes and submit outbox commit or roll back together. Provider acceptance is after commit and cannot roll back start charges.

Charge only eligible UPDATE transitions into `not_started`, including imported `ready/uploaded` when the approved use case invokes that transition. Merely inserting a row already in that status does not trigger a debit. Ordinary start remains draft-only. Replay of a started row does not charge again, and a mixed batch cannot silently claim an already-started row as fresh success. YouTube draft-to-completed never enters this transition and remains free. Preserve P2 freemium/account exception rules rather than copying them into HTTP or routing.

For unknown URL duration, preserve admission with strictly positive available balance and defer deduction. At first eligible terminal ingestion, normalize provider duration, ceil to whole minutes, and call P2 with `skip_balance_check=false`. Use a savepoint for the debit: insufficient balance or a debit storage error must not poison transcript delivery. Persist `charged` or the concrete uncharged failure outcome with completion so a callback replay cannot attempt another charge. There is no new automatic debt collection policy. Known duration can be lowered by provider observation without refund; equal/higher leaves it unchanged. Soniox reads internal `metadata.duration_ms`, falling back to max token end, not an invented top-level internal field (`frontend/src/utils/soniox.ts:207-305`; Deepgram equivalent `deepgram.ts:324-423`).

A pre-completion database failure retries the whole local ingestion, leaving neither lines nor a debit; a committed uncharged completion remains uncharged on replay. Never mark completion and then run an independent debit transaction. Preserve zero-minute cases, including strict zero failure versus bypass zero-usage records, according to P2 rather than tightening the minutes check.

Hard-delete refund must include imported positive and negative consumption linked by subject, including packages owned by other accounts. Use the P2 repair seam that discovers and locks all affected account owners in sorted order before host deletion, then removes usage and recomputes affected package sums within the same transaction. Do not first lock only the deleting owner and later discover a lower-id owner. Recheck the discovered owner set after locking, restarting if necessary. Source anomalies cannot be newly inserted/rewritten by runtime, and no new legitimate charge may reference a tombstoned subject. The P2 owner must supply the concrete seam; P3 does not fork or weaken it. Account deletion must also handle usages on the deleting account's packages referencing surviving foreign subjects without cascading those unrelated jobs.

Failure/partial-error mail is transition outbox work with buyer/support targets and stable delivery keys, not `JobUpdated` on every edit. Reuse actual configured mail transport and per-target recovery, but keep event namespaces/claim ownership separate from P2 purchase events. A completed result with deferred billing error does not silently invent a buyer-failure email; follow the existing partial-error/support classification. Later AI/customer callbacks consume completion events only when their phase has a real implementation. Neither can make an already completed transcription fail.

## 6. Retention, consent and erasure

### Cleanup is not history filtering or account erasure

Preserve three independent meanings. The list applies the source calendar-month window and descending-id cursor/page size 20 unless `unlimited_history`; automatic transcript cleanup uses job creation at or before `now - retention_days - 1 day`; object retention is a storage/provider policy. The daily 02:00 UTC cleanup passes 30, therefore removes lines at 31 days inclusive, only for completed jobs and explicitly true `auto_delete_transcripts`. False/null keep lines, unlimited history does not opt out, metadata and derived AI records are not part of that source sweep. Do not replace this with a 30-day everything-delete query. `deleted_monthly` remains inert. Source: PRV-013 through PRV-017, PRV-029, PRV-032 through PRV-036, and `frontend/supabase/migrations/20251222100001_update_cleanup_functions_audit_schema.sql:80-138`.

The source history calculation uses JavaScript `setMonth` in browser local time, including month-end overflow (`frontend/src/dao/JobRepository.ts:147-158,181-205`). Port an explicit pure calendar calculation with a supplied clock/calendar context and golden month-end/DST cases; UTC clamping would be a behavior change. Preserve inclusive boundary and distinguish view filtering from authorization. A retained owned job absent from the list can still be loaded by id. New arbitrary expiry of that read would need a policy decision.

One scheduled-run identity per UTC slot plus the required PG advisory lock prevents duplicate work across replicas. Manual triggers authenticate separately and cannot impersonate arbitrary users. Session advisory locks use a dedicated checked-out connection released on every path; returning a locked pooled connection is forbidden. Scheduler APIs and history/audit queries are not public authenticated-user endpoints. Weekly Sunday 04:00 UTC scheduler-run cleanup keeps the source `90 + 1 day` cutoff; retired health schedules have an explicit retirement entry rather than a successful no-op cron.

Cleanup captures a fixed cutoff, discovers candidate owners, locks accounts in sorted order and jobs in stable order, then rereads preferences and eligibility. Preference updates take the same account lock. Freeze the candidate set for this run; newly completed eligible jobs wait for the next run. Count actual eligible lines under these locks before deletion. More than 100000 means zero deletion; exactly 100000 is allowed. A single bounded data transaction preserves that safety guarantee and can commit exact deletion counts plus the run's success state together. Dry-run reuses the exact predicate/parameter validation (7 through 365), counts opted-out users, and does not write an audit record; results are a snapshot, not a future guarantee.

The source audit promise is not established merely by its SQL text: the table CHECK accepts only `success/failure/partial`, while cleanup inserts `skipped/aborted`; its exception handler inserts a failure then re-raises, which cannot guarantee a durable row after rollback. Source: `20251222100000_move_cleanup_audit_to_audit_schema.sql:23-35`; `20251222100001_update_cleanup_functions_audit_schema.sql:50-78,101-125,174-203`. Correct this by creating a durable run record before work, committing terminal success with deletion, and recording failure/skip/abort in an independent transaction after rollback or lock rejection. Startup recovery resolves expired running records to explicit interrupted/failure outcomes; it never reports unknown deletions as success. Database outage may delay that audit finalization, which readiness/operations must expose. Include actor, cutoff, counts, elapsed time and redacted failure reason. Do not retain deleted transcript content in audit messages.

### Account erasure saga

The account operation uses a small persisted manifest with explicit steps, not arbitrary workflow nodes. A request by the authenticated owner establishes an account erasure barrier and captures local/remote resource identities before any destructive cascade. All writers, worker claims, download/signing routes, billing provisioning and trusted directory refresh check that barrier. Provisioning must recheck it after acquiring/creating the locked account row and before grants commit; an earlier HTTP precheck is insufficient against deletion. The barrier survives removal of the account row. A stale valid JWT must not recreate the account or trial. Requests return accepted/pending until work is confirmed; an auth-admin error cannot return completed deletion. Client logout/reset follows an honest accepted/deleted state rather than a false success banner.

Steps, retried with claim lease and compare-and-swap:

1. Block new work and provisioning, fence attempts, snapshot objects/versions, remote provider ids, outstanding upload expiries and affected billing subjects. Suppress unsent user-content notifications and revoke application-held capabilities. No remote request occurs inside the account/ledger transaction.
2. Remove local transcript/dependent rows in explicit FK-safe order, invoke the fixed P2 hard-delete seam, remove owned jobs/payment/package/usage data as required and clear application caches. Persist the manifest independently of the account FK. Handle imported AI/API rows that exist, while later phases must add their own live producers and erasure participation before their gate can pass.
3. Delete private media, diagnostic payloads, staged URL objects and temporary outputs through their owning storage API, with generation/version-aware identities. Include Supabase's separate `jobs` bucket, not just GCS/R2: source raw payload writes are `frontend/src/utils/deepgram.ts:481-502` and `soniox.ts:386-405`. Supabase object metadata deletion in SQL does not delete bytes. Its object API supports listing and batched removal; authenticate through a restricted service adapter and inspect per-object outcomes. [Supabase Storage API](https://supabase.com/docs/reference/self-hosting-storage), [object deletion](https://supabase.com/docs/guides/storage/management/delete-objects).
4. Request provider cleanup for every known attempt, including superseded and late-bound attempts. Soniox cannot delete a currently processing transcription; 409 is pending cleanup, not success. Its transcription delete does not remove separately uploaded Files API objects. We submit URLs, but imported file ids must be accounted for. A 404 counts as absence only in the known project/region with verified credentials, not after accidentally changing project. [Soniox delete](https://soniox.com/docs/api-reference/stt/transcriptions/delete_transcription).
5. Delete the GoTrue identity using the trusted admin adapter; retain an erasure barrier sufficient to reject stale tokens and delayed webhook/provisioning writes. Supabase says existing access JWTs remain valid until expiry and owned Storage objects can prevent user deletion, so clear those owned objects first and keep auth failure pending. [Supabase user management](https://supabase.com/docs/guides/auth/managing-user-data). The runtime billing pool is never replaced by an auth/database owner pool.
6. Mark each resource confirmed, absent, blocked-until, retryable failure or unresolved. Finish only when mandatory steps are confirmed and explicitly approved retention exceptions are listed. A bounded worker pass, capped retry delay and durable pending state provide recovery without making up a finite remote-deletion guarantee. Operator retry uses the same manifest; it cannot assert success manually by removing evidence.

Local hard delete does not await a network transaction. The barrier precedes external calls so callbacks cannot recreate lines, exports or raw artifacts. A callback racing with erasure either commits before the manifest captures its resources or observes the barrier and contributes only remote deletion identity. Unknown submission outcomes remain unresolved resources until reconciled; expired leases are not evidence of remote absence. Minimize manifest personal data and remove resource payloads as steps finish; the retention of the final audit/tombstone needs an explicit operating policy, not a fabricated legal deadline.

This saga restores the source intended account cascade, including signed/cross-owner billing usage. It does not silently promote ordinary job soft-delete into physical erasure. Removing a draft should enqueue its orphan media cleanup; changing delete-all/read-by-id or retaining financial data beyond the source requires the decisions below. Source `PRV-007` preserves orphan billing details/invoices; `accounting.Invoices.payment_id` RESTRICT and `subscriptions.user_id` NO ACTION can obstruct the source cascade (`frontend/supabase/migrations/20251130113249_remote_schema.sql:4247,4352,4357,4407`). Inventory/import must surface these dependencies; do not mark deletion successful by ignoring them.

GCS source infrastructure sets lifecycle age 30 and an unlocked 31-day retention policy (`Infra/infrastructure/terraform/main.tf:28-39`). Google's documentation confirms that even an unlocked active retention policy blocks early deletion/replacement and lifecycle waits for retention expiry. Thus a new erasure worker cannot honestly promise immediate GCS removal without an approved policy change; record `blocked_until` and retry. R2 lifecycle configuration is absent from the source evidence, and soft-delete/versioning/backups require deployment evidence. [GCS bucket retention](https://docs.cloud.google.com/storage/docs/bucket-lock).

Deepgram documents default model-improvement retention; `mip_opt_out=true` stops content retention after processing, but request metadata remains, and async results remain until delivery/retry exhaustion. It documents no transcript retrieval after that point. Recommend an explicitly recorded privacy correction adding the opt-out flag, with exact-wire proof; do not label default requests zero-retention or invent a delete endpoint. [Deepgram data policy](https://developers.deepgram.com/trust-security/your-data). Soniox's source optional post-completion deletion remains configurable, but enabled deletion must happen only after durable ingestion and be retried. Account erasure separately tracks all provider artifacts, including failures.

EU processing is unresolved for the complete 61-language offer: Deepgram Whisper is not on the EU endpoint, while the source legal copy promises EU storage (`PRV-057`). Soniox regional processing uses a region-specific project/key/domain, not just a region string in a global request. This conflicts with a blanket EU claim even if all eight language codes are documented. No automatic cross-region fallback, no silent Nova replacement and no claim that dropping RunPod solved residency. [Soniox residency](https://soniox.com/docs/data-residency), [Deepgram regional limitations](https://developers.deepgram.com/trust-security/your-data).

### Consents and operational authority

P3 implements the current consent record contract: missing means false, version `1.0`, provider `deepseek`, grant/refusal timestamps and revoked state, and owner-only read/write. Likewise account deletion does not currently cancel subscriptions: continuing remote charges after local erasure requires a mu decision and a P2 cancellation integration, not an invented P3 payment policy.
