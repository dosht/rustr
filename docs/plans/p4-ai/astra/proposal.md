## 4. Generation, parsing and stream protocol

### Start, reconnect and recovery

1. Authenticate with existing identity; acquire account then job lock, fresh-read barrier/consent/content/flags, validate input, classify freemium and admit. Create pending generation and durable claim before network. Never hold a database transaction across LLM calls.
2. A worker claims once, records execution token and dispatch intent, then calls the adapter. No automatic replay after dispatch uncertainty. Reclaiming an expired worker fences that token; staged final data may be settled without a new provider call. Unknown in-flight requests become interrupted with external outcome unknown, not silently restarted.
3. Durably commit parsed analysis sections before publishing `sectionReady`. For prose, buffer deltas only within configured bounds, periodically store sanitized provisional snapshot with a sequence watermark, and publish provisional raw text to connected viewers. A crash may discard the uncheckpointed suffix, never advertise it as persisted. Final sanitation operates on the complete raw answer, not independently on tokens.
4. Transport disconnect detaches the observer, not the generation. Reconnect to the same id returns the latest authoritative snapshot and watermark, then later events. It may replace provisional text; it must not duplicate text or launch another provider call. Use a bounded local ring for connected clients, NOT a required durable replay log. On overflow/gap, resnapshot from DB; watch can land on either replica. Poll durable snapshot on the other replica; notifications are latency optimization only.
5. Retry is explicit new identity after a terminal/interrupted result; analysis replacement atomically clears old content and advances current pointer. Repeated retry key is idempotent. Preserve partial content before explicit retry. Chat failure does not insert a completed assistant pair; an already persisted success replay never spends quota again.
6. Transcript edit invalidates active generation publication/commit and marks any displayed cached result stale; keep already stored results readable as stale until retry/revoke. No automatic regeneration/cost. General completion summary is not automatically regenerated on every edit. Source-retention sweep fences any active generation and drops its temporary copied transcript; existing derived artifacts follow source retention policy.
7. Clock-derived pending/partial staleness uses source created_at thresholds. Worker total timeout is separate. Recommend 60s local total deadline for user analysis/chat and 30s for background summary, configurable explicitly. These are proposed enforced values, not claims source fetch enforced configuration. A stale/expired execution can never resume committing simply because it later receives bytes.

HTTP: retain session analyze/chat entry points as start-and-watch SSE conveniences; support idempotency key and returned generation id. Owner-scoped GET snapshot/watch and cancellation endpoints are additive. Prestream failures return JSON HTTP status; poststream failures are typed SSE terminal events. SSE uses event ids `generation:seq`, proper UTF-8/CRLF/multiline data parsing, comments/heartbeats, no proxy buffering/cache. Never put bearer credentials in query strings. Snapshot first, then cursor reconciliation prevents a subscribe/read gap. Heartbeats do not advance business progress. Client sequence gaps cause resnapshot, not speculative append; other-generation/old-epoch frames are discarded.

### Exact analysis parsing and source correction

Inspected source `frontend/src/pages/api/v1/ai/analyze.ts:77-96` parses **JSON documents only**. `:213-227` accepts JSON or legacy YAML syntax only for `documentCount`. Discovery AI-003's broad “legacy YAML fallback” overstates this route. Preserve the fallback header, not an invented general YAML parser; lead should correct that ledger wording with this source citation.

Source splits every literal `---`, including one inside a JSON string, silently skips parse failures, and marks completion even after ordinary EOF. Its prompt (`prompt-templates.ts:111-125`) says documentCount includes the header, but source subtracts only detectedType, yielding one too many visible content sections. Correct these explicitly:

- Accept one optional count header, JSON `{documentCount: N}` encoded as valid JSON or the exact legacy `documentCount: N` line; no YAML objects, aliases or arbitrary YAML evaluation.
- Split on a standalone three-hyphen line outside a JSON string/object, accepting LF or CRLF and chunk splits at any byte. A string containing `---` is data. Buffer one unfinished document. Parse final trailing document once at provider finish.
- Header N counts header + detectedType + content: visible content total is `max(N - 2, 0)`. If header absent, total is unknown until observed; do not invent progress. A present count inconsistent with received documents is `incomplete_output`, keeping valid partial sections, not completed success.

Specialized sections obey source schema optionality/types/enums, including interview ratings 1..5 and meeting default status pending. Only relevant optional sections are required; never fabricate empty sections to reach the count.

### Sanitation, bounds and errors

Use source JavaScript UTF-16 code-unit length for caps/estimates; Rust byte length or Unicode scalar count silently changes commercial outcomes. Input sanitation removes script blocks/tags, filters SQL words/javascript/event handlers, normalizes whitespace, then applies captured card/SSN/email/phone/key regexes. Output sanitation removes tags/javascript, normalizes whitespace and redacts; it does NOT apply the input SQL keyword filter. Analysis preserves raw speaker/text input as source does. Display untrusted text safely in every shell; sanitation is not a provider privacy guarantee.

Recommend explicit configurable operational caps: 16 MiB decoded request envelope, 1 MiB provider SSE event, 1 MiB total generated UTF-8 content, 256 KiB per analysis document, JSON depth 32, 64 documents, 64 KiB connected-client queue, and 8 simultaneously dispatched generations per process. These are new safety limits, not source allowances or commercial output-token limits; lead records them. Existing narrower chat character limits still apply. History exceeding the envelope is rejected with 413, never truncated to 50 messages. Analysis above envelope limit is likewise rejected, not summarized from an undisclosed prefix. Before reading full bodies enforce byte bounds; gzip cannot evade decoded bounds. Account-level quota admission and process capacity refusal return distinct busy codes; a capacity refusal before dispatch does not spend quota. No unbounded per-client copy of output; slow consumers receive resnapshot/disconnect instead of blocking the worker indefinitely. Provider reads yield to storage checkpoints; storage outage stops dispatch/consumption rather than accumulating buffers.

Errors distinguish invalid input/roles, not found, consent required/revoked, erased account, disabled feature, quota exhausted with which counter/reset, busy, persistence unavailable, provider rejection/rate limit, timeout/unknown completion, invalid/truncated output and stale source. Never expose prompts, provider body, auth headers or customer text in public errors/logs. Raw deltas are provisional and can transiently contain patterns later redacted; do not claim real-time PII removal. Final authoritative replacement is sent before completed state. On persistence failure keep the preview and `sync_warning`; no durable-completion claim and no blind repeat provider call.

## 5. Quota reservation and settlement

Source facts checked directly in `ai-service-manager.ts:204-282`, `chat-validator.ts:80-289`, `content-processor.ts:77-80`, baseline SQL `:656-725,816-832`. Configured production snapshot is 50 questions/20000 estimated tokens per transcript and 500 questions/50000 per user/day, not enforcement proof.

Admission under account lock:

- Use billing facet 3. Known paid: no quota storage lookup, reset, reservation or increment. Still enforce ownership, consent, message validation and operational bounds. Snapshot paid/freemium eligibility at admission; plan changes midstream do not retroactively charge or erase an admitted spend.
- If freemium and any cap enabled, admit at most one active quota-bearing generation per account. One durable record references the generation and all enabled counters, their effective caps, period identities and question estimate. The lock is released before HTTP. Another distinct request returns `CHAT_BUSY` while this one runs; same request returns its snapshot. This avoids arbitrary output allowance while making all completed spending sequential. Do not implement a hidden unbounded queue.
- Preserve check precedence: transcript questions, user questions, transcript tokens, user tokens. Question gate uses stored max_limit; token gate configured max. Preserve source absent/zero handling through existing config parsing; negative but parsed values are not silently changed to unlimited. Migration must not normalize away captured stored question maxima. No SQL procedure owns these decisions.
- On success, sanitize full response once, compute `ceil((question_utf16 + answer_utf16)/4)`, atomically append the pair, add one to each enabled question counter and this estimate to each enabled token counter, mark generation completed, and release reservation. The input reservation is replaced, not added again. No provider-reported token count replaces this commercial estimate.
- A failed/interrupted/canceled local generation with no durable successful final result releases the reservation without a successful-chat increment, retaining source success-only charging. Record that remote provider cost/completion may still be unknown. This release is a local commercial decision, NOT proof of provider cancellation. Fence late results before releasing, so late completion cannot settle the released reservation.
- Stage final sanitized payload durably under the same fences before attempting terminal settlement. Crash after staging can finish the local transaction without another model call. If no durable final survives a crash, generation becomes interrupted and no success settlement is invented. A DB outage can prevent even staging; viewer sees sync warning/interruption, never false durable success. No automatic paid regeneration to “recover” lost content.
- Initialize/reset on check at or after reset_date. UTC next day, ISO Monday next week, first next month. Bind admission to the applicable period; late settlement goes into that period's bucket, never a freshly reset next bucket. Limits GET does not reset an active generation's reserved period underneath it. Old buckets can be compacted after all reservations settle; transcript counters never reset. First insert must preserve its calculated reset, not overwrite it from an absent SELECT result. Existing null-reset imported timed rows need explicit migration repair using current period; historical reset placement is a P9 evidence gap, not a guessed reconstruction.
- Counter/storage failure before dispatch is 503; plan lookup failure still chooses freemium. Postgeneration storage failure is visibly unsynced, not silently discarded increment. This deliberately changes AI-019 availability to make limits enforceable.

## 6. Consent, erasure and completion summary
