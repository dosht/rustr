## Confirmed by source (no finding)

- **Ownership and barrier.** Every store entry calls `Tx::lock_account` first, which takes the advisory lock, checks the barrier and then reads the enrollment. That call is made directly or through `summary_source` (`store/summary.rs:21-29`, `store.rs:705-715`). The work is selected by `id AND account_id FOR UPDATE`, and generations by `id AND account_id AND work_id`. A stranger read returns NotFound (`pg_tests.rs:77-78`).
- **Atomic erasure.** `erase_data` copies minimal `llm` facts (generation, provider and remote_id, never text) from every generation that has a provider. It then deletes the works, which cascades to generations, staged finals and summaries. All of this happens in the existing transaction after the account key (`store.rs:484-499`, migration FKs). Late metadata under the barrier only touches the resource row and reopens the erasure (`store/summary.rs:210-231`). The erasure pass marks `llm` resources unresolved and never auto-excepts them (`app.rs:802`). P3 key sweeps already keep erasures open, so this adds no new non-completion behavior.
- **Request identity.** `UNIQUE(account_id, request_id)`. A replay on another work returns Conflict. Admission is serialized by the account lock, and a unique partial index allows one active generation per work (`store/summary.rs:73-101`). When a start COMMIT is lost, the client retries with the same id and gets the same generation back.
- **Claim before provider, no replay.** `claim_summary` commits `Running`, `remote_outcome_unknown=true` and `provider` before the transcript leaves the store (`store/summary.rs:104-125`, `domain.rs:83-90`). An unknown claim COMMIT returns without dispatch (`app.rs:84-90`). A non-Accepted generation is never claimed again. Interruption after the lease never dispatches again (`pg_tests.rs:133-138`).
- **Staged final and restart.** Every mutating path except cancel (see F5) reconciles first: admit, claim, read, settle and interrupt. A durable staged final completes locally, and the canonical summary upsert and generation completion share one transaction (`store/summary.rs:45-69`, `pg_tests.rs:83-96`). If the settle COMMIT is lost, `interrupt_summary` reconciles before it interrupts (`store/summary.rs:191-201`).
- **Retention.** `purge_transcript` bumps the revision (`work.rs:487-490`). `Source::permits` then fences active work, while the saved summary is preserved and new admission is refused (`pg_tests.rs:98-107`).
- **Bounds.** The transcript is checked with `octet_length` against the 16 MiB input limit minus the prompt before it is loaded (`store/summary.rs:110-117`). Output is bounded by the reducer's `StreamError::OutputLimit` (`llm-core/src/lib.rs:221,226,234`) and the 1 MiB check in the domain. Watch frames carry one cumulative snapshot under the D4 envelope.
- **Watch authority.** The first body pull authenticates again and reads the generation again, as does every later poll. An account mismatch, erasure, NotFound or NotEnrolled produces `Revoked`. An identity or storage outage produces a non-durable `Interrupted` control, so the reducer keeps `durable_seq` (`http.rs:99-131`, reducer `:208-244`). The `after` cursor is rejected when it is ahead, and a resnapshot at an equal sequence is still applied.
- **Disclosure without consent.** Start requires `external_processing_accepted: true`. Taskr has no consent or quota copy (`app.rs:39-41`).

## Findings

| ID | Sev | Finding and evidence | Impact |
|---|---|---|---|
| F1 | P2 | **Watch polling is an unbounded locking write path on the shared runtime pool.** Each attachment loops every 100 ms (`http.rs:104`): JWT verify, then `SummaryService::generation` → `read_summary_generation`, which opens a transaction, takes `pg_advisory_xact_lock` on the account, `SELECT … FOR UPDATE` on the work row and generation row, may reconcile/write, then commits (`store/summary.rs:21-36,127-134`). No per-account, per-generation or per-process attachment cap exists. The drive tick does the same at 10 Hz (`app.rs:137-139`). The pool is the billing runtime pool shared with billing and audio work (`compose.rs:185,241`). | One authenticated caller can open many watch streams for the duration of a generation (≤ lease, re-attachable). That serializes all of its own account's audio work, worker checkpoints and erasure barrier behind the advisory lock, and it ties up shared pool connections that billing and other tenants also use. D4 bounds subscriber memory; this DB/lock fan-out is unbounded. |
| F2 | P3 | **Claim neither renews nor checks the remaining lease against the provider deadline.** The lease is fixed at admission + 65 s (`store/summary.rs:93`) and never updated. The claim only requires `now < lease_until_us` (`domain.rs:84`). The drive then allows the full 60 s `CompletionRequest` timeout (`app.rs:95-96`, `llm-core/src/lib.rs:52`). Checkpoints and stage after the lease interrupt (`store/summary.rs:158-162`). A replayed start spawns a drive for a still-Accepted generation at any point in its lease (`app.rs:44-62`), for example after the admitting process died before claiming. | A late claim dispatches a billed provider request that cannot be saved and is interrupted with "source or execution lease no longer current". On the normal path the margin is 5 s minus admission→claim latency. |
| F3 | P3 | **No host regression covers `drive/consume` or `watch`.** Domain tests exercise `Generation`, and PG tests exercise store primitives only. Nothing in taskr-work drives `SummaryService` with a controlled `Llm`, or the watch route, for: claim-before-open ordering; local and remote cancel during a quiet provider; the tick's status/execution fence; Metadata/Finished after cancel or erasure; `settle` lost-COMMIT recovery through `interrupt_summary`; or watch first-pull re-auth, session-loss `Revoked` and resume. The contract requires "actual host restart/reconnect/cancel flows" (`implementation-contract.md:52`). The pending Playwright/UniFFI runs cover one fixture provider flow through these paths. `pg_tests` are `#[ignore]`. | These paths have evidence only from reading the code until the pending runtime proof lands. Whether artifact604 ran `summary::pg_tests -- --ignored` against a DB is not stated in what I was given. |
| F4 | P3 | **Cancel from another replica is not seen during `llm.open`.** While the transport is opening, only the local `Notify` races it (`app.rs:111-121`). The DB tick that observes Cancelled, interrupted or erased state starts only after open returns (`app.rs:127-139`). `cancel()` notifies only the local map (`app.rs:73-78`). | A request sent to another replica keeps a local dispatch slot (one of the process's eight) and the provider read open until headers arrive or the 60 s deadline. CAS fences prevent any content write, so there is no correctness leak. |
| F5 | P3 | **Cancel drops a durable staged final without reconciling it.** `cancel_summary` calls `g.cancel()`, which clears `staged` (`store/summary.rs:182-189`, `domain.rs:120-126`). Every other mutating path reconciles first. | Suppose the process died after the stage COMMIT. A GET followed by a cancel leaves Completed, but a direct cancel leaves Cancelled and the final is discarded. Either outcome may be acceptable, because staged is not completed. The order dependence is not documented. |
| F6 | P3 | **Start checks run before replay resolution.** `accepted=false` returns 400 and a missing LLM returns 503, both before `admit_summary` looks up the request id (`app.rs:40-41`). | This departs from `hosts.md:9`: an exact replay should return 200 with the same generation, and the same id with a different payload should return 409. It also means a replay after a restart without LLM config returns 503, although saved state is readable. |
| F7 | P4 | **Error text misattributes a non-storage failure.** A provider remote id longer than 1024 bytes returns `Invalid` (`store/summary.rs:206`). `consume` maps it through `storage_error` (`app.rs:116,154,160,170`), so the persisted interruption says the saved generation could not be updated and asks the user to reconnect to reconcile. | The interruption reason is misleading. There is nothing to reconcile. |

## Questions to p1T (factual, no edit requested)

1. F5: should cancel reconcile a staged final first, or is cancel-wins-over-uncommitted-stage the intended rule?
2. Interrupted and cancelled generations keep their partial text, which is derived from the transcript, indefinitely after transcript retention. Only completed summaries are named in `hosts.md:10`. Is that intended?
3. Is it a deliberate decision, not an omission, that taskr has no per-account bound on concurrent generations? One account can occupy all eight process dispatch slots across its works. The contract excludes copying Transgate quota.
4. F1: is there an intended attachment cap or lock-free poll read that I missed outside `summary/`?

**p1T answers (relayed via lead, 2026-10-25; Taskr source held, no review edits):**
1. F5: in the current code, cancel wins over a stage that has not been committed, and a canonical Completed result is preserved. p1T confirms the order dependence is real, and no lead approval of that rule is recorded.
2. Terminal partials have no TTL or retention cleanup. Keeping them indefinitely after a transcript purge was never separately agreed or documented.
3. No per-account fairness policy or cap was established. The only limits are one active generation per work and the shared process limit of eight. p1T agrees that excluding Transgate quota does not justify the missing resource fairness.
4. There is no attachment cap or lock-free poll that I missed. p1T also searched `taskr-server` and compose and found no concurrency-admission layer. Every watch and drive tick still takes locks at 10 Hz.

p1T also confirms that F2 (lease vs deadline) and F6 (replay vs config/disclosure order) are real mismatches in the source. Neither was observed failing. Disposition rests with lead.

## Addendum: LLM metadata across deletion paths (focused cross-slice check)

Question from lead: Transgate showed that reading generation rows only at erasure time is not enough when earlier deletions remove them. Does taskr's known LLM metadata survive every supported deletion of content or work before account erasure, and can late metadata disappear after the cascade? This was the same kind of read-only source pass. The Transgate correction is owned separately by X/R.

**Confirmed by source.**
- Taskr has no route or store path that deletes a summary generation, a saved summary or a work before account erasure. The work routes are enroll, list/create, settings, account erase/status, show, upload URL, uploaded and callback (`http.rs:34-42`). The summary routes only start, read, watch and cancel (`summary/http.rs:22-26`). The only row deletions in `taskr_work` are in `erase_data` and `finish_erasure` (`store.rs:495-497,662`).
- Transcript retention only clears `works.transcript` and bumps the revision. The work, generation and summary rows stay (`app.rs:691-697`, `work.rs:487-490`).
- The sample-resource erasure that runs earlier in the same transaction only deletes `taskr_billing.sample_work/customers` (`taskr-billing/src/lib.rs:188-192`). No foreign key from billing or the sample cascades into `taskr_work` (`0001_work.sql:8-19`).
- In `erase_data`, `llm` facts are captured from every generation with a provider before works and enrollments are deleted (`store.rs:486-499`). The capture runs under the account key, and no claim can commit once the barrier exists.
- Only `RemoteOutcome::NotDispatched` clears `provider` (`store/summary.rs:212-218,237`). The current `llm-http` emits it only before the send, from configuration, capacity or request validation (`llm-http/src/provider.rs:35-128`). A Rejected outcome keeps the provider, so the generation is still captured.
- Late metadata under the barrier inserts or updates the `llm` resource from the in-memory claim and reopens the erasure (`store/summary.rs:210-231`). That includes the case after `finish_erasure` has deleted every resource row. Both paths take the account key, so they are serialized.

| ID | Sev | Finding and evidence | Impact |
|---|---|---|---|
| M1 | P3 | **One remote-id slot overwrites known provider identifiers.** `llm-http` first emits Metadata with the response `x-request-id` (`provider.rs:135,144`). The first body chunk `id` differs, so it replaces the id and emits Metadata again (`provider.rs:183-185`). Before the barrier, taskr overwrites `Generation.remote_id` (`store/summary.rs:236`). Only the last id survives into the erasure manifest. |
| M2 | P4 | **An observed id is lost when persisting it fails.** If `record_summary_remote` fails, or the 60 s `timeout` drops `consume` mid-write, consume returns an error and `interrupt_summary` records no remote id (`app.rs:96,116,154,160,170,191-201`). | The erasure manifest still records that a dispatch happened, through `provider`, but loses an identifier that was seen. This happens only on a database or deadline failure. |
