## Ledger evidence mechanics (check-prd.py)

- rules.md is generated from discovery topic files; check-prd ledgers compares rules.md rows against topic rows. So test refs and status are edited in `transgate/docs/discovery/billing.md` and rules.md regenerated by `scripts/assemble-discovery.py`.
- BUT assemble-discovery lint_rules requires status `ledger` for every row ("expected 'ledger' in P0"). Writing `tested` in billing.md will make the assembler fail. Lead must change the linter to accept ledger|tested|changed before any row can turn green. Gate issue to report.
- Test reference format: `cargo:<package>:<libtest name>`, several separated by "; ". check-prd runs `cargo test --locked -p <package>` and parses `test <name> ... ok`. Name is the libtest path, e.g. `allocate::tests::bil_013_breakdown_case_1` for unit tests, or `bil_013_...` for an integration test file function (integration test names have no file prefix in libtest output, so names must be globally unique per package to avoid ambiguity).
- Status accepted for gate: `tested` or `changed`.
- Postgres tests: if they skip without TASKR_TEST_DATABASE_URL they still print `ok`; that is false green. Need a rule: a Postgres-backed ledger test must fail (not pass silently) when the DB env is missing in the gate, or the gate must set the env. Confirmed: taskr-postgres tests return early with an eprintln and report ok.
- gate-transgate runs `check-prd.py ledgers` over all 914 obligations, so "billing rows green" needs a scoped mode (prefix filter BIL, FRE, CPN plus billing parity rows) that still runs the named cargo tests.

## Workspace facts

- Module crates may not depend on taskr-core (forbidden host). Billing core defines its own two-line BoxFuture alias, its own ids and clock. No extra shared-kernel crate.
- taskr-core times are `Millis` (i64 UTC ms). Billing needs calendar month stepping without deps: days-from-civil arithmetic in billing core, tested.
- taskr-postgres: sqlx 0.9, `sqlx::migrate!("./migrations")` inside `connect`. Two migrators sharing one `_sqlx_migrations` table collide on version numbers. Billing needs its own migration table or schema; verify the sqlx 0.9 API during implementation.
- Job batch start today: one UPDATE where id in (ids) and status = draft; the trigger runs per row in one statement, so a batch is all-or-nothing and later rows see earlier rows' ledger writes. Pass/fail is order independent; which package each job draws from depends on row order. Rust: ascending job id, one transaction.
- Production (production-facts.md): payments 6512 (2054 completed, 4354 pending, 103 failed, 1 canceled). BIL-078 says canceled is never written, production has 1. Completed gateways: 2052 iyzico, 1 bank, 1 Iyzico IBAN. Package names beyond the four: Master, Pay-as-you-Go-Add, pay-as-you-go, freemium-gift, one null. 98359 freemium packages vs 98383 users. USD_TRY_RATE 44 (integer).
- Iyzico protocol (frontend/node_modules/iyzipay 2.0.64): every call sends `x-iyzi-rnd` (random), `x-iyzi-client-version`, `Authorization: IYZWSv2 base64("apiKey:<k>&randomKey:<r>&signature:<hex hmac-sha256(secret, r + uriPath + JSON.stringify(body))>")` and `Authorization_Fallback: IYZWS <k>:<base64 sha1(k + r + secret + pkiString)>`. Endpoints: payg init POST `/payment/iyzipos/checkoutform/initialize/auth/ecom`; payg retrieve POST `/payment/iyzipos/checkoutform/auth/ecom/detail`; subscription form init POST `/v2/subscription/checkoutform/initialize`; subscription form retrieve GET `/v2/subscription/checkoutform/{token}`; subscription retrieve GET `/v2/subscription/subscriptions/{ref}`; cancel POST `/v2/subscription/subscriptions/{ref}/cancel` (exists, unused today). For GET, body is `{}` so the signature covers `r + path + "{}"`.
- `formatPrice` sends `parseFloat(price).toString()`, so a TRY amount of 393.35999999999996 is sent literally. USD amounts after `Math.round(x*100)/100` print as 2dp.
- Confirm (checkout/confirm.tsx): plans read the response envelope `status` (not a payment status) from subscription checkout form retrieve; payg reads `paymentStatus`. err thrown -> `failed`. Envelope `status: failure` without err -> `failed` (definite answer). No session or owner check on confirm. Only plans save `customer_id` (`data.customerReferenceCode`).
- Renewal (subscription-callback.ts + iyzicoRenewal.ts): body fields orderReferenceCode, customerReferenceCode, subscriptionReferenceCode, iyziReferenceCode, iyziEventType, iyziEventTime. Retrieves subscription by body ref (only to read customerReferenceCode), oldest payment by customer_id, inserts pending renewal with token = orderReferenceCode (23505 -> reuse), then conditional update `neq completed, neq status`. Renewal packages start at the renewal row insert time. Debug email EML-BIL-004 thrown. Response 200 echoes the request.
- Checkout init: plan order amount = catalog USD price (TRY: x rate), metadata.package from catalog; payg: special offer `hours*14.99` TRY; else `localeDiscount(hours*1.49)`, then `round2`, then coupon `calculateCoupon(coupon, total, "Pay-as-you-Go")`, then TRY conversion. Coupon id saved whenever the coupon exists and is unexpired (even if filter mismatched). Payment row inserted after Iyzico returns token. Callback URL from Host + x-forwarded-proto with a strict host check.
