# Privacy, retention and identity

Privacy today: account deletion is one auth admin call plus a database cascade (probably broken in production since July 2025, and the API still answers 200); retention is a daily pg_cron SQL sweep of transcript lines (31 days effective, per user opt-out on by default) plus a browser-side one-month list window with an operator-set `unlimited_history`; consents are an AI consent table with server checks, a client-only cookie consent that gates PostHog but not Google Analytics, Hotjar or New Relic, an archived translation beta table, and a `blocked` flag enforced on two YouTube routes only.
Identity today: hosted Supabase Auth (GoTrue) with email and password, magic link, Google and password reset through the Auth UI library, browser-only route guards, a mirror trigger chain from `auth.users` (profile row, freemium package, welcome hook), decorative Turnstile, a disabled fraud check and a per process rate limiter running on two replicas.
This file holds 60 PRV rules, 35 IDN rules, 31 defects, 55 parity rows, 3 cleanup functions plus a dry run, 3 schedules and 10 auth flows; production Auth settings, cron state and deletion state could not be read from the repo and are in Needs mu.

Effective retention: the cutoff adds one extra day, so `cleanup_old_transcripts(30)` removes lines of jobs created 31 days ago or earlier. A job exactly 30 days old is kept (test `test_boundary_condition_exact_30_days`, M:20251222000003:17-81). The age is `jobs.created`, not completion time. Only status `completed` jobs are cleaned. Jobs in `failed`, `deleted` or any other status never lose their transcript lines.

One-time data fix: `M:20251222000000_cleanup_orphaned_transcripts.sql` deletes `transcripts` rows whose job no longer exists and raises if any remain. `M:20251222000001` then adds the RESTRICT FK. Supporting indexes in `M:20251221200003` (`idx_jobs_created_at`, `idx_transcripts_job_id`, `idx_transcripts_created`, `idx_provider_health_metrics_recorded_at`, `idx_jobs_user_created`) and `M:20251221200001` (partial index on `auto_delete_transcripts=true`).

## Open questions for the design

1. Deletion saga: what are the ordered steps, which ones must succeed before the identity is deleted, and how is a half finished deletion shown to the user and retried? Is there a "deleting" state that blocks sign in?
2. What happens to the accounts stuck since 2025-07 (asked to delete, still present)? Finish them, or ask the owners first?
3. Financial records on deletion: anonymize and keep, or delete (PRV-D03)? This decides `modules/billing` schema (nullable owner, tombstone).
4. Is the retention sweep one global job (as today, 02:00 UTC) or lazy per user? Is the cutoff job creation time (today) or completion time (UI text says "completed more than 30 days ago")? Keep 31 days effective?
5. Should `unlimited_history` exempt the user from the sweep (PRV-D06), or only change the list? Who can set it: operators only?
6. Where does the history window live: a use case with a server clock (calendar month or 31 days), shared by web, CLI, TUI and mobile?
7. Does a sweep delete data of `deleted` jobs and their audio too (PRV-D05)? Is the file store lifecycle (30/31 days) kept as a second guard?
8. User mirror: dumb copy triggers on `auth.users` (GoTrue stays) or first request upsert in the Identity adapter? The freemium package and welcome email move out of triggers either way.
9. Identity port shape: does the Rust server call GoTrue REST (signup, token, recover, verify, user, logout) and our own screens replace the Auth UI library, or does the shell use GoTrue directly? How are sessions carried: cookie on web, bearer token in secure storage on Android and iOS, and for the CLI and TUI (GoTrue has no device flow; password prompt or API key)?
10. Token refresh: browser auto refresh today, no server refresh. Does the Axum server refresh a cookie session, or do shells refresh and the server only validates?
11. Consent port: cookie consent is a browser cookie today. What is the equivalent on native apps and the CLI (no cookie, no tracker)? Is consent stored server side too (the AI consent already is)?
12. Rate limiting for auth and the YouTube style limits across replicas: port with Postgres adapter, shared with the RTL topic.
13. Captcha: where is the token verified (GoTrue captcha setting or our use case) and how does a fake work in dev?
14. Blocked users: one guard at the actor level or per use case? Does it stop sign in?
15. Test strategy for the SQL test functions: Rust tests need a temporary Postgres; 9 SQL tests map to ledger rows PRV-014 to PRV-025. Which of the two INFO tests (threshold, lock) become real tests?
16. Do CLI, TUI, Android and iOS get rows for sign in, sign out and settings (consent, retention toggle, delete account)? None exist today, so they are new surfaces for the platform topic.
17. The privacy policy and terms are static content for the cms module; do the conflicting numbers (14 days, 1 month, 30 days) get fixed in the port or after?
