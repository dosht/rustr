# Billing, payments, packages, freemium, coupons and currency

Source paths are relative to `/home/mu/Business/Transgate`. pgTAP references are `file:line` inside `frontend/supabase/tests/`. The final database state is the baseline `frontend/supabase/migrations/20251130113249_remote_schema.sql` plus the later migrations named in each row; no production database was read, so "final" means "what the migrations produce" (see Needs mu).

1. Balance is never stored. It is derived on every read from `packages` (minutes with a start and end) minus `usage_history` (one ledger row per deduction per package). Jobs are billed by a database trigger when a job goes to `not_started`; the trigger and the balance functions are plpgsql that went through 15 migrations after the baseline.
2. Money comes in through Iyzico only (hosted checkout form): pay-as-you-go packs of 5 to 9999 hours at 1.49 USD per hour, and four real recurring Iyzico subscription plans (Premium and Business, monthly and yearly). A completed payment row fires a trigger that creates the packages. Every new user gets a free 20 minute package that lasts 2 months, plus a first-job bypass.
3. Coupons are a small table with a product filter and apply to pay-as-you-go only. Currency is USD, or TRY for the `tr` locale at a fixed rate of 44 per USD. There is no refund path. The Paraşüt e-invoice flow and the invoice form are out of scope.

TRY amounts: checkout stores the USD price times the rate (44 by default) when the currency is TRY: 616 (Premium monthly), 924 (Business monthly), 5280 (Premium yearly), 7920 (Business yearly); for pay-as-you-go it stores `round2(hours x 1.49) x 44` without rounding after the multiplication; the special-offer buyers pay `hours x 14.99` TRY. The price Iyzico actually charges for a TRY plan is the TRY plan price held at Iyzico (not in the repo). Rules: CPN-001 to CPN-007.

Yearly expansion rule (database, not catalog): a payment with `metadata.package.count = N`, `interval = month`, `frequency = F`, `expiry = E` creates N packages. Package i (1 to N) starts at `payment.created + (i-1) x F months` (added step by step) and ends at its start plus `E months`. For the yearly plans that means 12 packages of 1200 or 2400 minutes, each valid for one calendar month, and each month's unused minutes are lost at its end. `interval = year` adds years instead of months; any other value raises an error. Source: `supabase-routines/DDL.sql:228-245`, `frontend/supabase/migrations/20251130113249_remote_schema.sql:883-903`, pgTAP `030-payment-trigger-tests.sql:231-430`.

### Is there a real recurring subscription, or only packages?

Both. The four plans are real Iyzico subscriptions: Iyzico stores the card and charges again every month or year, and tells the app through `/api/subscription-callback`. The app has no scheduler of its own for billing. Each charge becomes a new `payments` row and a new set of packages through the same trigger. Cancellation is manual: the app flags the payment and emails support, who must cancel at Iyzico by hand (`frontend/docs/arch42/appendix/billing-and-pricing.md`, section "Subscription Cancellation"; `frontend/src/pages/api/cancel-subscription.ts:22-26`). Pay-as-you-go is a one-time package. The Stripe-shaped `subscriptions` table is never written.

### Invoice data captured

- `billing_info` (name, company, address, country, tax id, Paraşüt contact id) is read by the billing history page and the admin endpoint; no screen or API writes it. The page `/InvoiceForm` collects the same kind of data but its submit handler only calls `console.log` (`frontend/src/pages/InvoiceForm/index.tsx:48-52`), and no link points to it.
- The billing history page (`/billing`) has no link from the live UI (its only link is in the dead `BillingInfo` tab), so customers reach it by typing the address or by support instructions. It lists the signed-in user's `completed` payments and draws a PDF invoice in the browser: invoice id `TRAN` plus the payment id padded to 8 digits, a hard-coded seller block (name, address, tax number, support email), the buyer block from `billing_info` or the account name, one line item, VAT 20 percent included in the amount for TRY and 0 percent for other currencies (`frontend/src/pages/billing/index.tsx:155-306`, id helper `:308-311`, page `:339-716`).
- The Turkish e-invoice (Paraşüt) is created outside the app by CLI tools and a Claude skill: `frontend/src/utils/parasut/**`, `frontend/faturas/`, `frontend/docs/product/epics/FTRA-1-fatura-automation/FTRA-101-fatura-draft-automation.md`. Out of scope, not ported.

### Admin invoice endpoint

`POST /api/admin/customer-invoices` with `{ "email": "<customer email>" }` (`frontend/src/pages/api/admin/customer-invoices.ts:8-90`): 405 if not POST; 401 without a session; 403 unless feature flag `BILLING_CUSTOMER_LOOKUP` is on for the session email (the flag is globally off with an allow-list of two admin emails, `frontend/src/utils/featureFlags.ts:108-114`); 400 without an email; 404 if no user has that email; otherwise 200 with `customer` (`email`, `full_name`), all `completed` payments newest first (`select *`), and the latest `billing_info` row or null. It reads with the service role. The `/billing` page shows the lookup box only when the same flag is on, and also lets that admin type a free-text "Bill To" block that replaces the buyer block on the PDF (not saved).

## Defects

Nothing here is changed by this document. "Current" is what the code does today (rule ids point to the ledger above). "Intended" is what the business clearly wants. "Proposal" is for mu to accept or reject. Items marked "needs mu" change a business outcome and must not be applied silently.

P2 implementation decisions are recorded in `docs/plans/p2-billing/decisions.md`: D1 allocator conservation/expiry, D2 measured exact-pricing differences, D3 payment/security corrections, D4 explicit initial-order alias resolution and D5 provider uncertainty. They authorize only the named corrections under PRD section 2; rule rows remain unverified until executable evidence passes. In particular, zero-minute bypass usage remains valid, manual cancellation remains a support request, and explicit Needs mu defaults are unchanged.

## Research

This topic owns none of the questions R1 to R5. It owns the billing part of PRD 7.5 (the migration dry run) and answers the topic questions below.

Short answers:
- Which billing page is live? The purchase screen is the billing dialog from `frontend/src/features/billing/**`. The history and invoice page is `/billing` (`frontend/src/pages/billing/index.tsx`, flag on for everyone, no link from the live UI). `/NewBilling` is a static demo and `/InvoiceForm` is a stub that saves nothing.
- Is there a real recurring subscription? Yes, four Iyzico plans (see Inventory); cancellation is manual at Iyzico.
- Where do prices come from? From code (`frontend/src/domain/packages.ts`), read by the landing pricing cards and the billing dialog. The database holds only purchases.
- Are there crons? No billing cron. Expiry is the clock.

### What the migration must carry

For PRD 7.5, "balances per user: old function versus new derivation must match to the minute". The old SQL function chain and the new derivation, with what to compare. Always evaluate both at the same fixed instant T (the time of the snapshot, as a UTC value), never at `now()`, otherwise packages that expire between the two runs create false mismatches.

| Old (SQL, in the snapshot) | New derivation (Rust) | Compare |
|---|---|---|
| `get_user_packages_with_balance(T)` | open packages at T with `remaining = minutes_included - sum(usage rows)` | per package: `package_id`, `minutes_included`, `minutes_consumed`, `remaining_minutes`; exact |
| `get_user_balance(T).balance`, and `user_balance_view.balance` when T is now | `balance(user, T)` = sum of remaining over open packages (BIL-004) | per user, exact minutes. A user missing in the old result must equal 0 or absent in the new one (BIL-008). Negative values are legal (BIL-009) |
| `request_breakdown_over_packages(R, T)` | `allocate(R, open_packages)` | for every user, with R in {1, 15, 60, remaining balance, remaining + 1}: `request_minutes` and `carry_over_minutes` per package. Skip users with two open packages that share an `end_at` (DEF-016) and list them |
| effect of `insert_new_packages_on_payment_completed` | `grant_packages(payment)` (BIL-044 to BIL-045) | for every `completed` payment compare the set of (`name`, `minutes_included`, `start_at`, `end_at`) with the old `packages` rows that have that `payment_id`. The dry run must reproduce the iterative month stepping (DEF-014) |

## Open questions for the design

1. Ledger shape. Keep one row per deduction per package, as today (the balance and the dry run both derive from them), and add a `reason` column (`job`, `bypass`, `adjustment`) so a refund or a correction is a new row, never an edit. Or add a stored `minutes_remaining` per package, updated in the same transaction (the read model in `docs/thoughts.md`). The migration dry run must still re-derive from rows.
2. LemonSqueezy orders to packages. Pay-as-you-go lets a customer pick any whole number of hours (5 to 9999) at 1.49 USD; LemonSqueezy sells fixed variants unless the checkout is created with a custom price through its API. Which: fixed bundles (for example 5, 10 and 25 hours, the UI presets), or a custom price per checkout? Which catalog entries does LemonSqueezy sell at all, given "no subscriptions"? Each paid order becomes a `payments` row (`payment_gateway` `lemonsqueezy`, `token` the order id, `completed` when the order is paid) and goes through the same `GrantPackages`.
3. Currency and gateway choice. Today the only rule is: UI locale `tr` pays in TRY through Iyzico at 44 per USD, everyone else pays USD through Iyzico. With two gateways, who decides: the customer (a button, as the "TR card, pay in TL" link is today), the locale, or the country? LemonSqueezy is the merchant of record and bills in the store currency, so the TRY rule and the fixed rate stay Iyzico-only. Which gateway gets customers whose Iyzico subscription fails (BILL-114)?
4. Invoices for LemonSqueezy orders. The PDF in `/billing` assumes Iyzico data and the Turkish VAT rule (CPN-018). For a merchant-of-record order, show the LemonSqueezy receipt link instead, or draw the same PDF?
5. Package start time and month stepping (DEF-013, DEF-014): copy the current behavior or fix it. This changes the dry-run expectations for yearly payments.
6. One definition of freemium (DEF-019) and the first-job bypass: preserve the distinct web 20/45-minute guard, SQL completed-job eligibility, and strict deferred callback deduction (FRE-019), or approve a unified rule. Combining them changes outcomes.
7. Unknown duration (DEF-017): hold a minimum at start, charge what is left and go negative, or refuse delivery when the deferred charge fails.
8. Catalog storage: code constants as today, a data file in the module, or a database table. The pricing site (PRD P6) must read the same data. Plan codes per gateway belong with each plan.
9. Events the module needs on the outbox: `UserCreated` (grants freemium), `PaymentCompleted` (grants packages, sends the two emails), `JobStartRequested` (charge), `ProviderAnswered` (deferred charge), `PaymentFailed` (analytics only).
10. Special clients and the special-offer buyers (CPN-007, CPN-019): move the 725 user ids and the two offer emails into data (a coupon plus an eligibility list) so no personal data is in source.
