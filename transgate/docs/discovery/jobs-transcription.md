# Jobs, upload, sources and transcription pipelines

Phase 0 discovery for the job lifecycle, upload and sources, transcription providers and pipelines, retries and recovery, and the schedules that drive jobs. Paths are relative to `/home/mu/Business/Transgate`. Read-only; nothing in that tree was changed.

Today a job is one row in `jobs` with a 12-value status enum, driven by three writers: the browser (Supabase client, draft rows), the Next.js server (submit, provider callbacks) and a Python GPU worker (RunPod, direct DB writes). Web jobs go draft -> not_started -> running -> completed or failed; the billing trigger fires on the not_started step. Soniox async (webhook, default), Deepgram (webhook, 5 slot queue) and RunPod/WhisperX share one table and no common state machine; retry, recovery and queue rules are spread over 3 schedulers and 5 files, with check-then-act guards and no idempotency key.
Files go browser -> signed PUT URL -> bucket (`transgate-audios`); the browser measures duration (whole minutes, rounded up). YouTube is a separate caption pipeline that never touches balance; URL, record audio, tab capture, Google Drive and OneDrive are not job sources in the web app today (API audio URLs and free tool pages only).

### 2.4 Pipelines

Common web entry (the "unified" service). The browser calls `POST /api/v1/transcriptions` with `{jobIds, locale}` (`frontend/src/features/transcription/services/FileUploadService.ts:108-111`). The route authenticates (session cookie for web, API key for API clients), validates (`frontend/src/app/api/v1/transcriptions/route.ts:564-721`: jobIds are positive integers; `audioUrls` allowed for API clients only; not both) and calls `TranscriptionService.processTranscription` (`frontend/src/services/unified-transcription/services/transcription.ts:73-209`). For job ids the service does, in one HTTP request: load the draft jobs under the user's RLS client (`:278`), `checkBillingAndBalance` (`:395-422`), `checkFraud` (`:427-433`, which always returns false because the body is disabled, `frontend/src/fraud.ts:4-5`), T04 (`:441-484`), then for each job in sequence pick the provider and call it (`:489-593`). It answers 201 after the provider accepted the audio, not after completion. Result per job: `{jobId, status, estimatedCompletionTime, error}`; metadata carries `newBalance`, `isFreemium`, counts. The old `/api/transcripts` and `/api/v1-beta/transcriptions/*` go through `BackwardCompatibilityMiddleware` into the same service (`frontend/src/pages/api/transcripts.ts`, `frontend/src/app/api/v1-beta/transcriptions/url/route.ts`). `/api/unified/transcriptions` only answers 301 "moved" (`frontend/src/app/api/unified/transcriptions/route.ts`).

- Deepgram and Soniox both set `started_at` and `transcription_provider` in the same write that flips to running, so a job routed by default is relabelled by the provider that actually accepted it.

### 2.5 Provider routing rule as coded

Two layers decide the provider. Only the first rows below are live for web jobs. Inputs: `job.transcription_provider`, `job.duration` (minutes), `job.translate_to` (non-empty means a translation job), the file extension of `job_name` (lower case), `job.language` (null means auto detect), the API request option `preferredProvider`, the client type (`web` or `api`), env `SONIOX_MAX_DURATION_MINUTES` (default 250). Output: one provider name. Source of the layers: `frontend/src/services/unified-transcription/services/transcription.ts:495-558` (layer 1) and `frontend/src/services/unified-transcription/services/provider-manager.ts:226-407` (layer 2).

Layer 1, `processJobsWithProvider`
1. If `job.transcription_provider` is not null, use it as is. No health check, no capability check (`transcription.ts:507-515`). The column default in the baseline is `deepgram` (see Needs mu).
2. Otherwise call layer 2 and write the answer to `jobs.transcription_provider` (`:516-522`, `:598-611`).
3. Call the provider. If the result is not a success and `options.fallbackEnabled !== false` (default true), run failover (`:542-558`).

Layer 2, `ProviderManager.selectProvider`, first match wins
1. Existing provider on the job: valid by `validateProviderChoice` then use it (never reached from layer 1 because layer 1 handles it first).
2. `job.duration > SONIOX_MAX_DURATION_MINUTES` and not a translation job: `deepgram` (`provider-manager.ts:273-288`; ADR-015). No availability check.
3. File extension `qta` and not a translation job: `deepgram` (`:296-309`).
4. `options.preferredProvider` set and valid: that provider (`:312-324`).
5. Language preference from the hard coded map `languagePreferences[job.language or 'English']`: Arabic, Indonesian, Japanese, Korean, Chinese, Urdu, Tamil all map to `soniox`; used when valid (`:168-175,342-351`).
6. Client type preference: `api` -> `soniox`, `web` -> `soniox`, when valid (`:193-196,354-361`).
7. Fallback chain `['soniox','deepgram','runpod']`, translation jobs keep only providers that support translation (only Soniox and Soniox v5), sorted by health score `successRate*0.5 + (100 - min(100,errorRate))*0.3 + max(0, 100 - avgLatencyMs/1000)*0.2` high to low; first valid one wins (`:1392-1518`).
8. Last resort: first of `soniox, deepgram, runpod` that can handle the job and is available; translation jobs filtered the same way; if nothing is left a translation job throws "Translation jobs require Soniox, but Soniox is unavailable"; a non-translation job gets `soniox` (`:1523-1606`).
9. Any exception: translation jobs rethrow, other jobs get `soniox` (`:380-397`).

`validateProviderChoice` (`:1112-1183`): the provider exists and `canHandle(job)`; a translation job needs a provider with `supportsTranslation`; `isAvailable()`; health: success rate at least 95, average latency at most 30000 ms, fewer than 3 consecutive server failures. Health is computed from the `jobs` rows created in the last hour for that provider; only server side error codes count (`provider_error, provider_unavailable, invalid_api_key, timeout, network_error, rate_limited, internal_error, database_error`; `provider-manager.ts:30-39`); average latency is always 0 because the table has no completion time (`frontend/src/services/unified-transcription/services/provider-manager.ts:950`, `health-monitor.ts:401`); any error while computing health means "assume healthy" (fail open). The `isHealthy` flag itself is `successRate >= 95 and errorRate <= 5 and consecutiveFailures < 5` (`provider-manager.ts:970`, same in `health-monitor.ts:421`), which is a different number from the 3 failure limit used when choosing. `HealthMonitor` also emails support when a provider turns from healthy to unhealthy (`frontend/src/services/unified-transcription/services/health-monitor.ts:230-245`). `ProviderManager` is constructed per request, so its 30 second health cache does not outlive a request.

`canHandle` per provider
- Soniox and Soniox v5: the language is null (auto detect) or one of the 53 supported (`providers/base.ts:118-129`, `providers/capabilities.ts:34-55`). Excluded: Armenian, Icelandic, Maori, Nepali, Georgian, Latin, Uzbek, Luxembourgish (`capabilities.ts:37`). Translation targets are the intersection of translation capable providers' languages = the same 53 (`capabilities.ts:121-138`).
- Deepgram: language must be non-null (auto detect is refused so it never gets a worse transcript) and in the 61 `supportedLanguages` (`providers/deepgram.ts:52-61`). Availability needs an API key and `5 - 1 - running Deepgram jobs > 0` (`deepgramRetry.ts:194-219`).
- RunPod: any of the 61 languages, API key present, no translation (`capabilities.ts:88-105`). Capability file size 25 MB, not enforced.
- Capability tables also list max concurrent jobs (Deepgram 5, Soniox 100, RunPod 10) and max file size (Deepgram 2 GB, Soniox 10 GB, RunPod 25 MB); no code enforces file size.

Failover (`provider-manager.ts:516-594`): chain minus the failed provider, translation jobs filtered to translation capable ones, first provider that is available, can handle the job and whose `transcribe` returns success wins and gets written to the job. Works after a 429 because the job is back in `pending`. Does not work after a hard failure: Soniox has already written `failed` and Deepgram refuses any status except pending or not_started (`utils/deepgram.ts:128-132`). Note the two SONIOX_V5 comments describe a feature flag that does not exist in code.

### 2.9 Transcript storage shape

- One row per line in `transcripts` (2.2). No words, no confidence, no paragraphs, no per word times.
- Time format `HH:MM:SS`, floor to the second, zero padded. Soniox lines add a 500 ms shift to both start and end before flooring (`SonioxProvider.TIMESTAMP_OFFSET_MS`, `frontend/src/utils/soniox/transcript-processor.ts:9-18`). Deepgram lines have no shift (`deepgram.ts:313-319`); the Deepgram provider declares a 500 ms constant that is not applied to lines.
- Speaker text is `SPEAKER_NN`. Soniox speaker numbers start at 1 and are stored as `SPEAKER_{n-1}` two digits (`transcript-processor.ts:104-106`); Deepgram speaker numbers start at 0 and are stored as is (`deepgram.ts:265`). RunPod format is written by the worker. The UI shows "Speaker {NN+1}" (`frontend/src/utils/formats.ts:57-63`).
- Lines without a speaker take the speaker of the previous line in the view (`applySpeakerFallback`, `frontend/src/features/transcriptLines/domain/mappers.ts:122-139`). Nothing is written back.
- Translation jobs store original and translation lines in the same table, told apart by `translation_status`; translation lines copy the time range of the paired original (`transcript-processor.ts:259-386`).
- Raw provider payload: a JSON file per job in the `jobs` bucket (2.2).
- Segmentation of Soniox tokens (non translation): skip audio events; start a new line when the previous token ends with `. ! ? ؟ 。 ！ ？`, or ends with `، , ; ؛` and the gap is over 300 ms, or the gap is over 2000 ms, or the speaker changes and speakers are on. Then merge: punctuation only lines, lines starting with punctuation, zero length lines, and lines shorter than 1 s with fewer than 3 words join the previous line; leftover zero length lines get 1 s or the neighbour's edge (`transcript-processor.ts:40-165,443-549`).
- Segmentation of Deepgram: one line per sentence of each paragraph, speaker from the paragraph; fallback by words with a 2 s gap rule. The fallback compares a time string with `parseFloat` (`parseFloat("00:01:23")` is 0), so in that fallback every word after the first two seconds starts a new line (`deepgram.ts:284`). The fallback only runs when the payload has no paragraphs.

### 2.11 Realtime and polling in the UI

- Job list and sidebar: one Supabase Realtime channel `db-job-changes` on `jobs` INSERT and UPDATE for the signed-in user (RLS applies), always on in the home page (`frontend/src/dao/JobRepository.ts:438-464`, `frontend/src/pages/home/[[...jobId]].tsx:126-133`). INSERT is needed so YouTube jobs that start `completed` appear without refresh.
- Job page: same channel filtered to the job id while not `completed` or `failed`; plus a 2 s poll of `getJobById` while `running` or `speaker_labeling` (`TranscriptLinesContainer.tsx:169-235`). A mutex ref makes sure completion is handled once.

- Upload queue page: the same job channel for status; duration is polled with back off (2.6).
- No server sent events, no websocket owned by the app server.

## Research

### R1: provider language coverage and the RunPod gap

The application's capability contract gives Deepgram and RunPod all 61 languages. Soniox and Soniox v5 exclude Armenian, Icelandic, Maori, Nepali, Georgian, Latin, Uzbek and Luxembourgish, leaving 53. Translation uses the intersection of translation-capable providers, also those 53. Source: `frontend/src/services/unified-transcription/providers/capabilities.ts:13-38,64-104,121-137`; exact names and ISO mappings belong to `languages.md`.

No language in that contract is RunPod-only: Deepgram covers the eight Soniox exclusions. This is application routing evidence, not a successful provider smoke or a vendor guarantee. Dropping RunPod removes a fallback and its Whisper options, incremental GPU output and grammar correction, not an identified language from the declared list. Deepgram capacity and actual acceptance of the eight excluded languages need recorded fixtures and later authorized provider verification. Do not infer coverage from the stale comments saying 57 or 46 languages.

### R2: translation is not an LLM call

The live translation path sends Soniox `translation.type=one_way` and the first target's ISO code. It stores paired original and translated lines. Models are `stt-async-v3` and, for explicitly selected v5 jobs, `stt-async-v5`. Sources: `frontend/src/services/unified-transcription/providers/soniox.ts:123-186`, `frontend/src/services/unified-transcription/providers/soniox-v5.ts:135`, `frontend/src/utils/soniox/transcript-processor.ts:178-386`. AI analysis and the old RunPod correction path are distinguished in `ai.md`; no separate translation LLM should be invented.

### R4: sources versus free tools

Signed-in YouTube add/resolve is a real job source but resolves captions, not uploaded audio, and skips the billed `not_started` transition. API audio URLs are real paid/deferred-billing jobs. Anonymous YouTube transcript downloads create no job. Recording and tab-capture tools export local files that can later be uploaded; their existence does not make them signed-in job sources. Sources: `frontend/src/pages/api/youtube/resolve.ts:105-158`, `frontend/src/services/unified-transcription/services/url-job-creator.ts:130-155`, `frontend/src/pages/api/youtube/public-transcript.ts:33-146`, `frontend/src/features/transcription/containers/TranscriptionContainer.tsx:173-180`. Preserve those boundaries; free-tool page coverage belongs to `static-pages.md`, voice-demo scope to `ai.md`.

Production context from `../production-facts.md:15,37-39`: Soniox duration threshold is 200 minutes, not the code default 250; recent jobs include 690 caption-source jobs and 773 external-URL jobs. Nine rows still have deprecated statuses. Migration must preserve/read those rows instead of assuming the historical statuses are absent.

## Needs mu

- The deployed default for `jobs.transcription_provider` is not established by the read-only production report. The baseline says Deepgram, while selection prefers Soniox when null (`frontend/supabase/migrations/20251130113249_remote_schema.sql:1426`; `frontend/src/services/unified-transcription/services/transcription.ts:505-522`). Assumption: preserve explicit row values and make new-job routing explicit in the new core; obtain schema/default evidence before migration.
- Actual Deepgram acceptance and quality for the eight Soniox-excluded languages is not verified by the capability list. Assumption: keep all language choices and the Deepgram route; no silent removal and no claim of provider validation.
- Cloud Function deployment and bucket lifecycle policies are not established by repository source. Assumption: browser duration plus callback reconciliation is the supported path, and retention requires an explicit object-deletion design rather than assuming storage cleanup.
- Production has nine deprecated-state rows (`../production-facts.md:38`). Assumption: import their original statuses for audit and let a migration decision explicitly classify them; do not silently discard them.
- YouTube bypasses billing today. Assumption: preserve this outcome unless mu approves a recorded rule change, even though the feature appears inside the paid application.

## Open questions for the design

- What atomic claim covers provider submission, callback ingestion and recovery so parallel replicas cannot buy duplicate transcriptions or insert duplicate lines?
- How should a callback received after deletion or cancellation be recorded without resurrecting content?
- Which export defects are approved fixes rather than compatibility requirements? Keep the decisions separate from transcription text and language parity.
- How will external audio URLs be revalidated at fetch time, and how will storage objects participate in deletion and retention?
- Which fixture corpus proves segmentation, speaker changes, paired translations, minute rounding and the eight non-Soniox languages before RunPod is removed?
- Scheduler ownership and cadence are cross-referenced to `platform.md`; billing trigger assertions stay with `billing.md`. No CRN, EML or FLG rules are owned here.
